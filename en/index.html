    The HTML, CSS and JavaScript domain 1.0 tests

    The web half of the first domain. Few questions, and all easy to get right once you recognise the vocabulary.

    The object-oriented PHP Drupal 11 assumes

    Why nearly all module code became classes, and what Drupal expects from those classes.

    In Drupal 7 a module was a pile of loose functions inside a .module file. From Drupal 8 onward that changed: most code became classes, and Drupal stopped calling your functions and started instantiating your classes. Understanding that inversion is what makes the rest of this course feel natural.

    1. Where the file lives defines the namespace

    Drupal uses PSR-4 autoloading: it finds a class's file from the class name, with nothing for you to declare. The rule is fixed — your module's src/ directory maps to the namespace Drupal\module_name, and each subfolder adds one more level.

    FileNamespace + class
    cert_lab/src/CertLabHelper.phpDrupal\cert_lab\CertLabHelper
    cert_lab/src/Controller/PageController.phpDrupal\cert_lab\Controller\PageController
    cert_lab/src/Plugin/Block/MyBlock.phpDrupal\cert_lab\Plugin\Block\MyBlock

    If the namespace doesn't match the path, the class simply "does not exist" as far as Drupal is concerned — a class not found error with no better clue. It is the number one cause of a module that won't install.

    2. An interface is a contract, a class is an implementation

    An interface lists the methods someone promises to have, without saying how. That matters in Drupal because the framework almost never cares which class you used — it cares whether it honours the contract.

    // src/CertLabHelperInterface.php — the contract
<?php
namespace Drupal\cert_lab;

interface CertLabHelperInterface {
  // signature only. No body.
  public function latestArticles(int $limit): array;
}

    // src/CertLabHelper.php — the implementation
<?php
namespace Drupal\cert_lab;

use Drupal\Core\Session\AccountInterface;

class CertLabHelper implements CertLabHelperInterface {

  // Constructor property promotion (PHP 8): declare and assign at once.
  // Equivalent to creating $this->currentUser and assigning it in the body.
  public function __construct(
    protected readonly AccountInterface $currentUser,
  ) {}

  public function latestArticles(int $limit): array {
    // ...
    return [];
  }
}

    3. The golden rule: type hint against the interface

    Notice the constructor asks for AccountInterface, not User. That choice shows up in several exam questions, so it is worth understanding the reason instead of memorising it.

    • Substitutable: Drupal may hand you the logged-in user, an anonymous user or a proxy object. All three satisfy AccountInterface. Demand User and you break with the other two.
    • Testable: in a test you pass a mock that implements the interface — no database and no real user needed.
    • It is the core pattern: nearly every Drupal service has its interface (EntityTypeManagerInterface, ConfigFactoryInterface, MessengerInterface). PHPCS with DrupalPractice complains when you stray from it.

    How this shows up on the exam: four constructor signatures, and the right one is the one that takes the interface.

    // ✅ takes the interface
public function __construct(AccountInterface $currentUser) {}

// ❌ concrete class: breaks with the anonymous user and with the proxy object
public function __construct(User $currentUser) {}

// ❌ takes nothing and fetches instead: hidden dependency, untestable
public function __construct() {}
public function something() { $u = \Drupal::currentUser(); }

// ❌ takes a generic array: loses the type hint and the autocomplete
public function __construct(array $config) {}

class CertLabHelper {
  use StringTranslationTrait;      // trait: "glues" methods onto the class

  public function label(string $name): string {
    // ✅ the trait gave the t() method to this class

    // return $this->t('Hello, ' . $name);

    About $this->t(): when your class extends a Drupal base class or uses StringTranslationTrait, you call $this->t('text') instead of the global t() function. In procedural files, t() is still valid. Neither ever takes a concatenated variable — always a placeholder.

    Services and dependency injection

    The most cross-cutting concept in modern Drupal. It comes back in plugins, forms, controllers and tests.

    1. The problem injection solves

    Picture a class that needs to know who the logged-in user is. The temptation is to fetch that information from inside:

    // ❌ the class goes and fetches what it needs
class Report {
  public function generate() {
    $user = \Drupal::currentUser();   // hidden dependency
  }
}

    It works — and it is wrong for three concrete reasons, not out of purism:

    • The dependency becomes invisible. Looking at the class signature, nobody can tell it needs the current user. You only find out by reading the body of every method.
    • The test can no longer be isolated. \Drupal::currentUser() requires an initialised container. You can't write a Unit test any more.
    • You can't swap the implementation. A module that wanted to decorate this service has no way in.

    The alternative is to invert it: the class declares what it needs and someone hands it over. That is dependency injection.

    // ✅ the class receives what it needs
class Report {
  public function __construct(
    protected AccountInterface $currentUser,
  ) {}
}

    2. Who hands it over: the service container

    The container is a catalogue of the site's reusable objects. Each entry has a name (the service ID), a class, and the list of other services it needs to be given. The container wires the whole graph on its own and only instantiates what the request actually uses.

    # cert_lab.services.yml — at the module root
services:
  cert_lab.helper:                              # service ID: use the module prefix
    class: Drupal\cert_lab\CertLabHelper
    arguments:
      - '@current_user'                         # @ = another service
      - '@entity_type.manager'

    The order of arguments must match the order of the constructor parameters exactly. A mismatch there raises a TypeError the moment the service is instantiated — not at cache rebuild time.

    Services you will run into for the rest of the course:

    Service IDWhat it is for
    entity_type.managerGet storage and handlers for any entity
    current_userSession user and their permissions
    config.factoryRead and write configuration
    logger.factoryWrite to the site log
    messengerStatus messages on screen
    databaseConnection for queries that aren't entity queries
    rendererTurn a render array into HTML
    cache.defaultCache bin for your own data

    3. How a Drupal class receives the injection

    A plain service gets everything through the constructor, and that's it. But controllers, forms and plugins are not instantiated by you — Drupal creates them. For those there is a static factory method: create().

    <?php
namespace Drupal\cert_lab\Controller;

use Drupal\Core\Controller\ControllerBase;
use Drupal\Core\Entity\EntityTypeManagerInterface;
use Symfony\Component\DependencyInjection\ContainerInterface;

class CertLabController extends ControllerBase {

  // 2nd: the constructor only receives and stores
  public function __construct(
    protected EntityTypeManagerInterface $entityTypeManager,
  ) {}

  // 1st: Drupal calls this method, which pulls from the container
  //      and returns the fully wired instance
  public static function create(ContainerInterface $container) {
    return new static(
      $container->get('entity_type.manager'),
    );
  }

  // 3rd: methods use the property, never \Drupal::
  public function page() {
    $nodes = $this->entityTypeManager->getStorage('node')->loadMultiple();
    return ['#markup' => count($nodes)];
  }
}

    new static() instead of new self() is deliberate: it guarantees that if someone extends your class, the subclass is what gets instantiated.

    The name of the factory method shifts a little depending on the kind of class, but the pattern is always the same:

    Kind of classInterface to implementSignature
    Controller, FormContainerInjectionInterfacecreate($container)
    Plugin (block, formatter…)ContainerFactoryPluginInterfacecreate($container, $configuration, $plugin_id, $plugin_definition)
    Plain servicenoneconstructor only; the YAML sorts it out
    Comes up often: the static \Drupal:: is only acceptable in procedural files — .module, .install, .theme — where there is no container to inject from. Inside any class, it is injection. If an answer uses \Drupal:: inside a class, it is almost always the wrong one.

    4. Extending the behaviour of an existing service

    Recurring scenario: "how do I change the behaviour of a core service without hacking core". Three mechanisms, from least to most invasive.

    Decorator — your service wraps the original. You intercept the methods you care about and delegate the rest. It is the preferred route, because the original stays intact and another module can decorate on top of yours.

    # cert_lab.services.yml
services:
  cert_lab.mail_decorator:
    class: Drupal\cert_lab\Mail\MailDecorator
    decorates: plugin.manager.mail          # which service to wrap
    arguments: ['@cert_lab.mail_decorator.inner']   # .inner = the original

    <?php
namespace Drupal\cert_lab\Mail;

use Drupal\Core\Mail\MailManagerInterface;

class MailDecorator implements MailManagerInterface {

  public function __construct(
    protected MailManagerInterface $inner,   // the original service
  ) {}

  // the method you want to change
  public function mail($module, $key, $to, $langcode, $params = [], $reply = NULL, $send = TRUE) {
    if ($this->isTestEnvironment()) {
      $to = 'qa@company.com';               // intercept
    }
    return $this->inner->mail($module, $key, $to, $langcode, $params, $reply, $send);
  }

  // everything else simply delegates
  public function getInstance(array $options) {
    return $this->inner->getInstance($options);
  }
}

    Note the name @cert_lab.mail_decorator.inner: when compiling the container, Drupal renames the original service with the .inner suffix and hands it to your constructor. You delegate to it for everything you don't want to change.

    ServiceProvider — alters the definition of a service in the container. Use it when a decorator won't do, for example to swap the class of a service that has no suitable interface. The file has a fixed name and place: src/CertLabServiceProvider.php, with the class named after the module in CamelCase.

    <?php
namespace Drupal\cert_lab;

use Drupal\Core\DependencyInjection\ContainerBuilder;
use Drupal\Core\DependencyInjection\ServiceProviderBase;
use Symfony\Component\DependencyInjection\Reference;

class CertLabServiceProvider extends ServiceProviderBase {

  public function alter(ContainerBuilder $container) {
    if ($definition = $container->getDefinition('breadcrumb')) {
      // swap the class that implements the service
      $definition->setClass('Drupal\cert_lab\CertLabBreadcrumbBuilder');
      $definition->addArgument(new Reference('entity_type.manager'));
    }
  }
}

    Tags — replace nothing. They register your service in a collection Drupal already consumes, and core calls everyone enrolled. That is how event subscribers, breadcrumb builders and param converters announce themselves.

    services:
  cert_lab.subscriber:
    class: Drupal\cert_lab\EventSubscriber\CertLabSubscriber
    tags:
      - { name: event_subscriber }

  cert_lab.breadcrumb:
    class: Drupal\cert_lab\CertLabBreadcrumbBuilder
    tags:
      # higher priority is consulted first
      - { name: breadcrumb_builder, priority: 100 }
    How to choose: want to change the behaviour of one service? Decorator. Want to add an implementation to a collection core already walks? Tag. Only when neither fits, ServiceProvider.

    Routing: from URL to controller

    The path a request travels before it becomes HTML — and the points where you step into that path.

    1. The request cycle, in seven steps

    Knowing this sequence answers several troubleshooting and performance questions on its own, because almost every "why isn't this happening" question is really a question about which step you tried to intervene in.

    #StepWhere you can step in
    1index.php boots the kernel and the container—
    2Page cache answers straight away, if anonymous and there is a hitCache metadata (module 5)
    3kernel.request eventEvent subscriber
    4Router matches the path to a route; parameters become objects*.routing.yml, param converter
    5Route access check_permission, _custom_access
    6Controller runs and returns a render arrayYour controller
    7Renderer turns it into HTML; kernel.response eventPreprocess, Twig, event subscriber

    Look at step 5: access is decided before the controller. That is why checking permissions inside the controller is considered wrong — you are stepping in too late.

    2. Anatomy of a route

    A route ties a path to a callable and to an access rule. All of it in cert_lab.routing.yml.

    cert_lab.report:
  path: '/cert-lab/report/{node}'
  defaults:
    _controller: '\Drupal\cert_lab\Controller\CertLabController::report'
    _title: 'Report'
  requirements:
    _permission: 'access content'
  options:
    parameters:
      node:
        type: entity:node      # upcasting: {node} arrives as a Node object

    Parameter upcasting is what turns the 7 in the URL into a loaded Node object before the controller runs. It also throws in the automatic 404 when the ID doesn't exist. Without it, the method receives the raw string and you would have to load and validate by hand.

    The controller receives the parameter by name, not by position:

    public function report(NodeInterface $node) {   // name matches {node}
  return ['#markup' => $node->label()];
}

    3. Which access key to use

    KeyWhen
    _permissionAccess depends only on a named permission
    _roleA specific role. Rare and discouraged
    _entity_accessnode.view, node.update — delegates to the entity access handler
    _custom_accessYour own logic. The method returns an AccessResult
    _access: 'TRUE'Genuinely public. Not a place to check access later in the controller
     
    requirements:
  _permission: 'access content'                  # one permission
  _permission: 'view report+administer nodes'    # + = OR
  _permission: 'view report,access area'         # , = AND

  _entity_access: 'node.update'                  # delegates to the entity handler
  _custom_access: '\Drupal\cert_lab\Access\ReportAccess::check'
  _access: 'TRUE'                                # public
    Why it matters: checking access inside the controller breaks the system. The menu link and the router believe the user can get in, the link shows up, and the 403 only appears after the click.

    4. Writing a _custom_access

    # in the route
requirements:
  _custom_access: '\Drupal\cert_lab\Access\ReportAccess::check'

    public function check(AccountInterface $account, NodeInterface $node) {
  // AccessResult, never a raw TRUE/FALSE
  return AccessResult::allowedIf($node->getOwnerId() === $account->id())
    ->addCacheableDependency($node)          // the decision depends on the node…
    ->cachePerUser();                        // …and varies per user
}

    Three details the exam tests: the return is an AccessResult object (allowed(), forbidden(), neutral()), the decision carries its own cache metadata, and forbidden() is not the same as neutral() — the first vetoes even if another module allows, the second merely abstains.

    5. Links and URLs in code

    Never write the URL as a string. Generate it from the route name, so it keeps working if the path changes:

    $url  = Url::fromRoute('cert_lab.report', ['node' => 7]);
$link = Link::createFromRoute($this->t('View report'), 'cert_lab.report', ['node' => 7]);

// URL coming from the user: validate it, don't trust it
$external = Url::fromUserInput($input);   // rejects javascript: and friends
    Common symptom: a new route returning 404. It is almost always the route cache (drush cr) or wrong indentation in the YAML. drush route shows whether the route was ever registered.

    Composer, patches and core updates

    How third-party code enters the project and why it is never hand-edited.

    1. The whole project is a package

    Modern Drupal is a Composer project. Core and all contrib come in through composer require; vendor/ and web/core are never hand-edited nor committed as the source of truth.

    composer require drupal/pathauto:^1.12
composer update drupal/core-* --with-all-dependencies   # updates core

    Two files govern everything, and the difference between them is on the exam:

    FileHoldsWho edits it
    composer.jsonWhat you ask for: ^1.12, version rangesYou (or the require command)
    composer.lockWhat was resolved: the exact version of each packageComposer only. But it goes into Git

    In production you run composer install (honours the lock, installs what was tested), never composer update (recalculates versions and can bring surprises).

    The commands that show up in the options, and what each actually does:

    CommandEffect
    composer require drupal/fooAdds to require and installs
    composer require --dev drupal/fooAdds to require-dev: skipped in production with --no-dev
    composer remove drupal/fooRemoves from composer.json and from disk. Uninstall the module first, or Drupal is left with orphaned config
    composer update drupal/fooUpdates only that package and rewrites the lock
    composer update --lockRegenerates the lock without changing installed versions
    composer why drupal/fooShows what requires that package. The answer to "why is this installed?"
    composer why-not drupal/core 11.1Explains what is blocking an update
    composer outdated --directLists newer versions among your direct dependencies
    Order the exam tests when removing a module: drush pm:uninstall foo first, composer remove drupal/foo after. Reversed, Drupal loses the module's class before it can run the uninstall, and you are left with dangling configuration.

    2. Patch: a fix that hasn't become a release yet

    You found the issue on drupal.org, the patch exists, but the maintainer hasn't published a new version. The right route is to declare the patch, with cweagans/composer-patches:

    "extra": {
  "patches": {
    "drupal/pathauto": {
      "#3401234 fixes alias on translation":
        "https://www.drupal.org/files/issues/2024-01-01/pathauto-3401234-7.patch"
    }
  }
}

    That way the patch reapplies itself on every composer install and survives the next update. Editing the file in contrib directly loses the fix silently — and nobody finds out until the bug returns in production.

    3. Updating core safely

    The sequence the exam expects to see:

    composer update drupal/core-* --with-all-dependencies   # 1. pull the code
drush updatedb                                          # 2. run pending hook_update_N
drush cache:rebuild                                     # 3. rebuild caches
drush config:export                                     # 4. capture config the update changed

    A patch release update (10.3.4 → 10.3.5) is safe routine: within a minor, Drupal introduces no API breaks. A minor update (10.3 → 10.4) calls for reading the release notes. A major update is a project of its own, with Upgrade Status and fixing deprecated code.

    Git and automated tests: the minimum tested

    Two lightly weighted subjects that still yield easy questions to get right.

    1. Git in a Drupal project workflow

    Git shows up in workflow scenarios: feature branch, rebase vs merge, what goes into the repository. Rule of thumb for what does not get committed: vendor/, web/core, web/modules/contrib, settings.local.php, user files (sites/default/files).

    # .gitignore for a Composer-based Drupal project

/web/core/
/web/modules/contrib/

/web/sites/default/files/

    What does go into the repository: your custom code, the composer.json and the composer.lock, and the exported configuration directory. That combination is what makes the site reproducible — someone else clones, runs composer install and drush cim, and has the same site.

    2. The Git commands the exam tests

    The questions are about workflow: given a problem, which command solves it.

    SituationCommand
    Bring in what changed on the remote without touching your workgit fetch (a pull = fetch + merge, and already changes your branch)
    Put your branch on top of the updated upstreamgit rebase origin/develop
    Turn 4 WIP commits into onegit rebase -i HEAD~4 and mark them squash
    Find which commit introduced a buggit bisect start / bad / good
    Take one specific commit to another branchgit cherry-pick <sha>
    Stash dirty work to switch branchesgit stash / git stash pop
    Undo a commit that is already publishedgit revert <sha>, which creates a new commit
    Clean up local branches gone from the remotegit fetch --prune

    Rebase or merge? Rebase rewrites history and produces a straight line: good on your branch, before opening the PR. Merge preserves history and is what you use to integrate into a shared branch. The rule the exam assumes: never rewrite history on a branch someone else is already using.

    Reset: --soft keeps the changes staged, --mixed (default) unstages but keeps them on disk, --hard discards everything. The option with reset --hard on a shared branch is always the wrong one.

    3. The four kinds of test

    All of them run under PHPUnit. The difference is how much of Drupal each one boots — and the more it boots, the slower it is.

    KindWhat it bootsUse when
    UnitTestCaseNothing. Plain PHPPure logic, mocked dependencies. Fast
    KernelTestBaseContainer + databaseA service using entity storage, config, plugin managers
    BrowserTestBaseFull site, no JSForm flows, permissions, pages
    WebDriverTestBaseSite + real browserOnly when you genuinely need JavaScript/AJAX
    Exam pattern: the right answer is always the cheapest test that still covers the scenario. If the scenario mentions entity storage but no browser, it's Kernel. If it mentions clicking and seeing something appear without a reload, it's WebDriver.

    Where the files live: tests/src/Unit/, tests/src/Kernel/, tests/src/Functional/, tests/src/FunctionalJavascript/. The folder defines the namespace and is how the runner finds each suite.

    Content entity vs config entity

    The most heavily tested distinction in the heaviest domain of the exam.

    1. What an entity actually is

    An entity is the abstraction Drupal uses for any stored "thing": an article, a user, a taxonomy term, an image. They all expose the same API — load(), save(), delete(), get(), set() — which lets you write code that works for any type.

    Three words come up constantly and get mixed up:

    • Entity type — the category: node, user, media.
    • Bundle — the subdivision of the type, with its own fields: article and page are bundles of node. Not every type has bundles (user doesn't).
    • Field — the data itself. A field always belongs to a bundle and is always a list of values, even when it holds only one.
    $node->getEntityTypeId();   // 'node'   → the type
$node->bundle();            // 'article'→ the bundle
$node->id();                // 7
$node->label();             // the title

// a field is always a list: these three lines do the same thing
$node->get('field_summary')->value;
$node->field_summary->value;
$node->get('field_summary')->first()->value;

// multi-value field
foreach ($node->get('field_tags') as $item) {
  $term = $item->entity;   // an entity reference already loads the object
}

    2. The two families

    They are two different storage systems, with different purposes.

    Content entityConfig entity
    HoldsContent created on the siteDefinitions and structure
    Lives inIts own database tablesConfig storage, exportable as YAML
    FieldableYesNo
    Revisionable / translatableYesNo (config has language overrides)
    Examplesnode, user, taxonomy_term, media, comment, filenode_type, view, image_style, view_mode, field_config, user_role
    Mental shortcut: if you expect the thing to differ between dev and production because of editorial work, it's content. If you expect it to travel with the code on deploy, it's config.

    3. The confusing pair: node type and node

    A content type called "Article" is a config entity (node_type): it defines the structure, it is exportable, and it travels on deploy. A published article is a content entity (node): it is content, it stays in the database, and it does not travel. The same logic holds for the vocabulary/term pair and for the view/view results pair.

    That is why creating a field in dev and exporting takes the field to production — but not the text someone typed into it.

    // config entity: loaded by machine name, and exportable
$type = $this->entityTypeManager->getStorage('node_type')->load('article');
$type->label();                       // 'Article'

// content entity: loaded by numeric ID, and stays in the database
$node = $this->entityTypeManager->getStorage('node')->load(7);
$node->bundle();                      // 'article' — points at the config above

    # the config entity above, exported by drush cex:
# config/sync/node.type.article.yml
uuid: 8f3e...
langcode: en
status: true
name: Article
type: article
new_revision: true

    There is no equivalent YAML file for node 7. Content isn't exported — it's migrated.

    Loading and saving entities the right way

    The route that goes through the entity type manager, and why it exists.

    1. Storage: the front door

    You never instantiate an entity with new, nor query its table directly. Everything goes through the storage handler for that type, which the entity type manager hands you:

    $storage = $this->entityTypeManager->getStorage('node');

$node  = $storage->load(7);
$nodes = $storage->loadMultiple([7, 8, 9]);        // ONE query
$byVal = $storage->loadByProperties(['type' => 'article']);

    The old procedural functions — node_load(), node_load_multiple(), entity_load() — have been removed. If they show up in an answer, it's a distractor.

    2. Create, change and delete

    3. The performance mistake the exam mixes in here

    // ❌ N+1: one query per iteration
foreach ($ids as $id) {
  $nodes[] = $storage->load($id);
}

// ✅ one query for all of them
$nodes = $storage->loadMultiple($ids);
    Why loadMultiple() wins: one query instead of N, and the storage static cache avoids reloading what is already in memory for that request. On an admin screen with 500 items, the difference is seconds.

    EntityQuery and the mandatory accessCheck()

    How to query entities without writing SQL — and the call that became mandatory.

    EntityQuery is how you ask "which entities meet these conditions". It knows nothing about tables: you filter by fields, and Drupal translates that to SQL (or to whatever the storage uses).

    $ids = $storage->getQuery()
  ->accessCheck(TRUE)              // mandatory since D10: omitting it throws
  ->condition('status', 1)
  ->condition('type', 'article')
  ->sort('created', 'DESC')
  ->range(0, 5)
  ->execute();                     // returns IDs, not entities

$nodes = $storage->loadMultiple($ids);

    1. Why accessCheck() became mandatory

    Up to Drupal 9, omitting the call meant "no access check" — and sites leaked unpublished content without anyone noticing. From Drupal 10 on, the decision has to be explicit: no call, exception.

    • accessCheck(TRUE) — any listing an end user sees.
    • accessCheck(FALSE) — only when the bypass is intentional: cron, a migration, or an admin screen already protected by the route's own permission.
    // ❌ without the call: throws, instead of returning unfiltered results
$ids = $storage->getQuery()->condition('status', 1)->execute();
// "Entity queries must explicitly set whether the query
//  should be access checked or not."

// ✅ a listing the user sees
$ids = $storage->getQuery()->accessCheck(TRUE)->condition('status', 1)->execute();

// ✅ deliberate bypass, inside a cron job that must see everything
$ids = $storage->getQuery()->accessCheck(FALSE)->condition('changed', $yesterday, '<')->execute();

    2. Conditions you will use

    $q->condition('title', 'Drupal%', 'LIKE');

$q->condition('field_summary', NULL, 'IS NULL');

    Detail that gets tested: execute() returns IDs, not entities. The next step is always loadMultiple(). Anyone expecting objects straight out of execute() gets the question wrong.

    3. When it isn't an entity: the Database API

    For your own tables or queries that don't map to entities, use the Database API — always with placeholders, never with concatenation:

    $this->database->select('watchdog', 'w')
  ->fields('w', ['wid', 'message'])
  ->condition('type', $userInput)   // the API does the binding
  ->execute();

// query with literal SQL: the :type placeholder is substituted safely
$this->database->query(
  'SELECT wid FROM {watchdog} WHERE type = :type', [':type' => $userInput]
);

    The braces in {watchdog} apply the table prefix configured for the site. Concatenating the value into the string is SQL injection — and it is the recurring distractor in the security domain.

    CRUD hooks: which one to use

    Where to hook code that reacts to an entity's life cycle.

    Every time an entity is created, saved or deleted, Drupal notifies modules through a sequence of hooks. Picking the right hook is picking the right moment — and the moment decides whether your change persists or not.

    hook_entity_insert()After the first saveReacting: send email, index, create a related record

    Generic or specific?

    Each hook has two forms. The generic one runs for every entity on the site; the specific one only for the type named in it:

    Prefer the specific one when you only care about one type: fewer calls per request, and the type hint is already right. Use the generic one when the behaviour applies to everything (auditing, for instance) — and then filter on $entity->getEntityTypeId().

    Hook, plugin or event subscriber?

    Drupal's three extension mechanisms, and how to choose between them under pressure.

    Recurring exam scenario: "what is the correct way to implement X". It isn't a syntax question — it is about recognising which of the three mechanisms Drupal reserved for that kind of problem.

    1. Hook — the advertised extension point

    Core carries out a task and, at chosen points, asks modules: "anyone want a say?". Every module that implemented that hook is called, in weight order. It is a one-way mechanism: you react or alter, but you don't decide the architecture.

    // cert_lab.module — the function name IS the registration. There is no YAML.
// pattern: modulename_hookname()
function cert_lab_node_presave(NodeInterface $node) {
  // core calls this on its own, every time a node is about to be saved
}

    2. Plugin — the interchangeable part

    Drupal defines a contract ("a block knows how to render and configure itself") and lets any module supply implementations. Then somebody chooses which one to use: the editor picks the block, the admin picks the field formatter, Views picks the filter. That choice is the signature of a plugin.

    // src/Plugin/Block/MyBlock.php — the folder and the attribute do the registration
#[Block(id: "cert_lab_mine", admin_label: new TranslatableMarkup("My block"))]
class MyBlock extends BlockBase {
  public function build() {
    return ['#markup' => 'hello'];
  }
}
// nobody calls this class. It becomes an OPTION on the block layout screen,
// and only runs if an editor chooses to place it in a region.

    3. Event subscriber — the reaction to something happening

    Inherited from Symfony. An object dispatches an event and whoever subscribed is notified, in priority order. Unlike a hook, the subscriber receives an event object it can inspect, alter, and even use to stop propagation.

    class CertLabSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    return [KernelEvents::REQUEST => ['onRequest', 100]];
  }

  public function onRequest(RequestEvent $event): void {
    // the event object carries state and lets you respond
    $event->getRequest()->getPathInfo();
    $event->setResponse(new RedirectResponse('/elsewhere'));
    $event->stopPropagation();     // lower-priority ones don't run
  }
}
// + the event_subscriber tag in services.yml, or nothing happens

    4. The decision table

    MechanismUse whenExample
    PluginThere are N interchangeable implementations of the same contract, and someone picks which to useBlock, field formatter, field widget, condition, migrate source
    HookReacting to or altering something core already does, at a foreseen extension pointhook_form_alter(), hook_entity_presave()
    Event subscriberReacting to a request-cycle event or to a service that dispatches eventsKernelEvents::REQUEST, config save, migration
    Short rule: plugin = something to be chosen. Hook/event = something to react to. A component the editor positions and configures is always a plugin (Block), never a hook.

    Writing a plugin: Block

    One plugin end to end. The pattern repeats in formatters, widgets, conditions and migrate.

    1. The three parts of every plugin system

    • The plugin type — defined by core: an interface, a base class and a plugin manager (the plugin.manager.block service).
    • Discovery — how the manager finds implementations. In Drupal 11, through a PHP attribute on the class, inside src/Plugin/<Type>/.
    • The implementation — your class.

    Event subscribers

    Reacting to the request cycle and to events dispatched by services.

    The pattern comes from Symfony: an object dispatches an event, and every subscriber is called in priority order, receiving the event object — which they can inspect and alter.

    if (!$event->isMainRequest()) { return; }   // ignore sub-requests

    Render arrays instead of HTML

    The structure that runs through Drupal's whole backend: describe the output, don't assemble it.

    1. Why not return HTML directly

    Drupal's backend describes what to render, it doesn't build a string. A render array is a structured array that only becomes HTML at the end of the request. That deferral is what makes the following possible:

    • Altering — another module can touch the structure before it becomes HTML.
    • Caching piece by piece — each fragment carries its own cache metadata.
    • Attaching assets — CSS and JS ride along with the element that needs them.
    • Escaping correctly — the renderer knows what is text and what is markup.
    // ❌ a string: none of that is possible afterwards
public function page() {
  $html = '<ul>';
  foreach ($nodes as $node) {
    $html .= '<li>' . $node->label() . '</li>';   // and no escaping!
  }
  return ['#markup' => $html . '</ul>'];
}

// ✅ structure: alterable, cacheable, escaped, with assets
public function page() {
  return [
    '#theme' => 'item_list',
    '#items' => array_map(fn($n) => $n->label(), $nodes),
    '#cache' => ['tags' => ['node_list']],
    '#attached' => ['library' => ['cert_lab/list']],
  ];
}

    Concatenate HTML in the controller and you lose all four at once. That is why the "build the string and return it" answer is always wrong.

    2. Anatomy

    Keys with # are properties; keys without # are child elements, rendered in #weight order.

    $build = [
  '#theme' => 'item_list',
  '#items' => $titles,
  '#title' => $this->t('Articles'),
  '#attached' => ['library' => ['cert_lab/list']],
  '#cache' => ['tags' => ['node_list'], 'contexts' => ['user.roles']],
];
    PropertyWhat it does
    #themeRenders through a theme hook and its template
    #typePredefined render element (container, link, table)
    #markupHTML filtered by Xss::filterAdmin() — for trusted markup only
    #plain_textFully escaped text — use this with user input
    #attachedLibraries, drupalSettings, http headers
    #cacheCache metadata: tags, contexts, max-age
    Tested directly: displaying a name typed by a user uses #plain_text. #markup still lets tags through and is an XSS vector. There is no #raw.

    3. Child elements and ordering

    $build = [
  'title'  => ['#markup' => '<h2>Articles</h2>', '#weight' => -10],
  'list'   => ['#theme' => 'item_list', '#items' => $items, '#weight' => 0],
  'footer' => ['#markup' => $text, '#weight' => 10],
];

    Lower weight comes first. That is how modules insert content in the middle of a structure another module assembled.

    4. Rendering by hand (and when not to)

    $html = $this->renderer->render($build);

    Calling the renderer directly is rare and dangerous: the fragment's cache metadata doesn't bubble up to the page, and you end up with stale content cached. The normal thing is to return the array and let Drupal render it. If you really must, renderInIsolation() exists to make it explicit that the context is isolated.

    Theme hooks, preprocess and suggestions

    From the PHP structure to the Twig template — and the points where the theme steps in.

    1. What #theme triggers

    When the renderer hits '#theme' => 'cert_lab_list', it looks up in the theme registry what to do: which template to use and which preprocess functions to call first. Registering a theme hook is filling in that registry entry.

    // cert_lab.module — registers a new theme hook
function cert_lab_theme() {
  return [
    'cert_lab_list' => [
      'variables' => ['items' => [], 'title' => NULL],
      // looks for templates/cert-lab-list.html.twig
    ],
  ];
}

// prepares variables for the template
function template_preprocess_cert_lab_list(&$variables) {
  $variables['total'] = count($variables['items']);
}

    The matching template receives the variables already prepared:

    {# templates/cert-lab-list.html.twig #}
{# file name: the theme hook with hyphens in place of underscores #}
<div class="cert-lab-list">
  <p>{{ total }} items</p>
  <ul>
    {% for item in items %}
      <li>{{ item }}</li>
    {% endfor %}
  </ul>
</div>

    2. The preprocess chain

    Several functions run in sequence before the template, each able to add or adjust variables. The order goes from most generic to most specific, and the theme speaks last — which is why the theme can always override the module:

    template_preprocess_cert_lab_list()    // 1. core / whoever defined the hook
cert_lab_preprocess_cert_lab_list()    // 2. modules
my_theme_preprocess_cert_lab_list()    // 3. the active theme — last word

    3. Varying an existing template

    To vary a template that already exists, the mechanism is a theme suggestion, not a new theme hook:

    function cert_lab_theme_suggestions_node_alter(array &$suggestions, array $variables) {
  $node = $variables['elements']['#node'];
  $suggestions[] = 'node__' . $node->bundle() . '__featured';
  // enables node--article--featured.html.twig
}

    Naming convention: PHP uses __ (two underscores), the file uses -- (two hyphens). The last item in the list has the highest priority.

    To discover the available suggestions: turn on Twig debug in your dev services.yml. The HTML then carries comments listing the candidate template names, with the chosen one marked with an x. It is the standard tool for this job — and it belongs in dev, never in production.

    Twig: autoescape and the danger of |raw

    1. The three constructs

    {{ variable }}      {# prints, escaping automatically #}
{% if x %}...{% endif %}   {# logic: if, for, set, block #}
{# a comment, never reaches the HTML #}

    2. Day-to-day syntax

    {{ node.label }}                        {# escaped automatically #}

    {{ x|default('—') }}Fallback value when empty

    4. Autoescape: the security rule

    Drupal's Twig escapes all output by default. |raw turns that escaping off and is the classic source of XSS.

    If HTML is "showing up as text" on screen, the cause is almost never a missing |raw — it is that you are printing the field's raw value instead of the rendered field:

    {{ node.body.value }}     {# ❌ the HTML appears escaped, as text #}
{{ content.body }}        {# ✅ rendered field, already sanitised by the text format #}

    That distinction — node.field.value is raw data, content.field is rendered output — solves most of the problems where the wrong answer would be |raw.

    t() placeholders: @var escapes (the default), %var escapes and wraps in <em>, :var is only for the href attribute. Never concatenate a variable inside the translatable string — the text has to reach the translator whole.

    Libraries, drupalSettings and behaviors

    How CSS and JavaScript reach the page, and how Drupal's JS differs from ordinary JS.

    1. Library: the unit of assets

    In Drupal you never point at a loose JS file. You declare a library — a named bundle with its CSS, its JS and its dependencies — and then attach the library wherever it is needed. That way Drupal resolves order, dependencies and aggregation on its own.

    # cert_lab.libraries.yml
list:
  version: 1.x
  css:
    component:
      css/list.css: {}
  js:
    js/list.js: {}
  dependencies:
    - core/drupal
    - core/once
    - core/drupalSettings

    The CSS group (base, layout, component, state, theme) defines load order and follows the SMACSS pattern Drupal adopted. Components go in component.

    2. Three ways to attach

    // PHP: attaches the library and sends data to the JS
$build['#attached']['library'][] = 'cert_lab/list';
$build['#attached']['drupalSettings']['certLab']['limit'] = 5;

    {# Twig: when the template is the one that knows it needs it #}
{{ attach_library('cert_lab/list') }}

    # the theme's *.info.yml: load on every page of the site
libraries:
  - cert_lab/list

    Always prefer attaching to the element that needs it: that way the asset is only downloaded on pages where the component appears. Loading everything globally is the performance mistake the exam ties to this topic.

    3. Drupal's JavaScript

    // js/list.js
(function (Drupal, once, drupalSettings) {
  Drupal.behaviors.certLabList = {
    attach(context) {
      // runs again for every new piece of content arriving via AJAX;
      // once() guarantees a single initialisation per element
      once('cert-lab-list', '.cert-lab-list', context).forEach((el) => {
        el.dataset.limit = drupalSettings.certLab.limit;
      });
    },
  };
})(Drupal, once, drupalSettings);

    ConceptProblem it solves

    Tags, contexts and max-age

    The subject most often failed by those who don't pass. Worth genuinely understanding, not memorising.

    1. The caching problem, in one sentence

    Storing the finished result is easy. The hard part is knowing when to throw it away and how many different versions to keep. Drupal answers those two questions with three pieces of metadata, and each answers a distinct question. Mixing them up is what produces both stale content and slow sites.

    2. The three metadata

    MetadataQuestion it answersExamples
    tagsWhich data does this depend on? When that changes, invalidatenode:7, node_list, config:system.site, user:3
    contextsAlong which request dimension does this vary? Keep one version per variationuser.roles, user, url.path, url.query_args, languages, theme
    max-ageFor how long does it stay valid?Cache::PERMANENT, 3600, 0
     
    $build['#cache'] = [
  'tags'     => ['node_list'],       // invalidates on any node save/delete
  'contexts' => ['user.roles'],      // one variation per set of roles
  'max-age'  => Cache::PERMANENT,
];
    The central trap: 'max-age' => 0 "fixes" any stale-content problem — and destroys performance. When the scenario says a listing doesn't update when new content is published, the right answer is the cache tag node_list, not switching caching off.

    Prefer user.roles over user: varying per user creates one cache entry per person; varying per role creates three or four across the whole site.

    3. The fourth key: keys

    Tags, contexts and max-age answer when to invalidate and how many variations to keep. keys answers something else: what the identity of that cache entry is. Without keys, an element is not stored in the render cache on its own — it merely inherits the caching of the page containing it.

    $build = [
  '#theme' => 'cert_lab_list',
  '#cache' => [
    'keys'     => ['cert_lab', 'list', $this->configuration['limit']],  // identity
    'contexts' => ['user.roles'],     // variations within that identity
    'tags'     => ['node_list'],      // when to throw it away
    'max-age'  => Cache::PERMANENT,
  ],
];

    The final cache ID is keys joined with the values of the contexts. In the example, an editor and an anonymous user produce two entries, and changing the limit from 5 to 10 produces two more: different identities, not variations.

    KeyQuestion
    keysWhat is this entry called?
    contextsAlong which dimension does it multiply?
    tagsWhen does it stop being valid?
    max-ageFor how long is it valid?
    Detail that gets tested: blocks, fields and entities rendered by core already have keys set by the system itself. You declare keys when you build your own render array and want that fragment cached independently.

    4. Tags: the ones you will use

    TagInvalidated when
    node:7That specific node is saved or deleted
    node_listAny node is saved or deleted
    node_list:articleAny node of that bundle changes
    user:3That user is changed
    config:cert_lab.settingsThat configuration is saved
    taxonomy_term_listAny term changes

    You rarely need to write the tag by hand: $node->getCacheTags() returns ['node:7'], and the standard for listings is $storage->getEntityType()->getListCacheTags().

    // manually invalidating a tag of your own (rare, but it comes up)
Cache::invalidateTags(['cert_lab:report']);

    5. How to decide, on the exam and in real life

    Ask the three questions in this order:

    • "What data does this depend on?" → each answer becomes a tag.
    • "Would two people see different things? Why?" → each "why" becomes a context.
    • "Does this expire on its own over time?" → only then max-age. Almost always the answer is no, and it stays Cache::PERMANENT.

    Applying that to a concrete case — a block listing the 5 most recent articles, with footer text coming from the site settings, and an extra notice visible only to editors:

    $build['#cache'] = [
  // Q1: what data does it depend on?
  //     → the node list, and the site config
  'tags' => ['node_list:article', 'config:system.site'],

  // Q2: would two people see different things? Yes — the editor sees the notice.
  //     → varies by role (not by user: that would be far too many variations)
  'contexts' => ['user.roles'],

  // Q3: does it expire with time? No. The tags handle invalidation.
  'max-age' => Cache::PERMANENT,
];

    If instead the block showed an exchange rate coming from an external API, then 'max-age' => 900 would be right: no Drupal tag knows when the rate changed, and time is the only possible answer.

    Bubbling and cache dependencies

    Why declaring on the component is enough, and how to declare without missing anything.

    Cache metadata bubbles up: what you declare on one piece of the render array propagates to the parent element and from there to the page. That is why declaring correctly on the component is enough — you don't need to touch the page.

    // the manual way
$build['#cache']['tags'] = Cache::mergeTags(
  $build['#cache']['tags'] ?? [], $node->getCacheTags()
);

// the preferred way: the entity knows how to declare its own dependencies
$meta = CacheableMetadata::createFromRenderArray($build);
$meta->addCacheableDependency($node);      // its tags + contexts + max-age
$meta->addCacheableDependency($config);
$meta->applyTo($build);

    Any object implementing CacheableDependencyInterface — entities, config, access results — can be passed to addCacheableDependency(). It is the preferred answer in "how do I declare the dependency correctly" scenarios.

    The bubbling composition rule is conservative, and it makes sense: the parent gets the union of its children's tags and contexts, and the lowest max-age among them. One child declaring max-age: 0 is enough to make the whole page uncacheable — that is how one badly written component drags down the performance of the entire site.

    How to check in practice

    curl -I https://site.test/page | grep -i x-drupal-cache

X-Drupal-Cache: HIT              # page cache (anonymous)
X-Drupal-Dynamic-Cache: MISS     # dynamic page cache
X-Drupal-Cache-Tags: node:7 node_list config:system.site
X-Drupal-Cache-Contexts: languages:language_interface theme user.roles

    If the tag you expect isn't in the header, it didn't bubble up — and the invalidation will never happen. It is the one-line test for any "why doesn't it update" question.

    Lazy builders, placeholders and the cache layers

    How to isolate the dynamic fragment without sacrificing the whole page.

    When a small, highly dynamic piece (the "hello, so-and-so", the cart) forces the whole page to vary per user, the way out is to isolate it in a placeholder rendered separately.

    $build['greeting'] = [
  '#lazy_builder' => ['cert_lab.lazy:greeting', [$uid]],  // scalar arguments only
  '#create_placeholder' => TRUE,
];

    The cert_lab.lazy service has a greeting($uid) method returning the render array for that fragment. Two requirements the exam tests: the arguments must be scalars (you can't pass a Node object), and the method must declare trustedCallbacks() for Drupal to agree to call it.

    That way the rest of the page stays cacheable, and BigPipe delivers the dynamic piece afterwards, streamed.

    Other performance levers in code

    • Your own cache for expensive results: $this->cache->set($cid, $data, Cache::PERMANENT, $tags) and get() before recomputing.
    • Queue API for heavy work: instead of processing 5,000 items in the request, enqueue them and let cron consume them.
    • Batch API when the user needs to see progress on a long operation started from the UI.
    • Avoid loading whole entities when only the ID matters: getQuery() already returns IDs.
    // your own cache for an expensive computation
$cid = 'cert_lab:report:' . $year;

if ($item = $this->cache->get($cid)) {
  return $item->data;                       // hit: doesn't even compute
}

$data = $this->computeHeavyReport($year);
$this->cache->set($cid, $data, Cache::PERMANENT, ['node_list']);
return $data;

    // heavy work: enqueue instead of processing in the request
$queue = $this->queueFactory->get('cert_lab_reindex');
foreach ($ids as $id) {
  $queue->createItem(['nid' => $id]);      // cron consumes it later
}

    Dynamic Page CacheAnonymous and authenticatedCaches the page with holes at the placeholders

    Sanitisation: escape on output, not on input

    The principle that organises Drupal's whole security domain.

    1. Why not sanitise on input

    Sanitising as you write looks simpler, and it is wrong: at write time you don't know whether that data will come out in HTML, inside an attribute, in a plain-text email, in JSON or in a CSV. Each destination needs a different escape. Sanitising early destroys the original data and protects the wrong destination anyway.

    // ❌ escaping on input: the data is corrupted forever
$node->set('field_name', Html::escape($input));   // stores "Jo&amp;#039;ão"
$node->save();
// the plain-text email will show the raw HTML entity,
// so will the CSV, and a second escape on output doubles everything

// ✅ store it as it came
$node->set('field_name', $input);                 // "Jo'ão"
$node->save();

// ...and escape per destination, at display time
$build['name'] = ['#plain_text' => $node->field_name->value];   // HTML
$subject = $node->field_name->value;                            // email: raw

    Drupal's principle: store the data as it arrived, escape at display time, according to the output context.

    2. The tool per context

    ContextTool
    Text in a render array'#plain_text'
    Text in TwigAutoescape (do nothing)
    String in PHPHtml::escape()
    HTML that must keep some tagsXss::filter() / Xss::filterAdmin()
    Value in a SQL queryDatabase API placeholder
    URL coming from the userUrl::fromUserInput() — rejects javascript:
    Classic distractor: htmlspecialchars() before concatenating into SQL. It is HTML output protection applied at the wrong layer — it does not prevent SQL injection. Each layer has its own tool.

    3. Text formats: who is allowed to write HTML

    In Drupal, permission to write HTML doesn't belong to the field — it belongs to the text format. Each format has a list of filters and a list of authorised roles. A format opened up to an untrusted role with the XSS filter switched off is an open door.

    Three warnings the exam presents as configuration scenarios, not code:

    • Full HTML format available to ordinary authenticated users.
    • The "Limit allowed HTML tags" filter disabled on a publicly used format.
    • Permissions like administer filters or administer users granted to a non-administrative role — they amount to full access to the site.
    // text the user wrote with a text format:
// render it THROUGH the format, which applies the configured filters
$build['body'] = [
  '#type' => 'processed_text',
  '#text' => $node->body->value,
  '#format' => $node->body->format,   // ← the filtering comes from here
];

// ❌ ignoring the format and dumping it into markup: no filter runs
$build['body'] = ['#markup' => $node->body->value];

    Access, CSRF, files and updates

    The rest of the security domain: what to protect beyond text output.

    1. Declaring and checking permissions

    # cert_lab.permissions.yml
'administer cert lab':
  title: 'Administer Cert Lab'
  restrict access: TRUE     # marks the permission as admin-equivalent

$node->access('update', $account);                // access to an entity

    The main check, though, belongs on the route — _permission or _entity_access. Code that checks afterwards is the wrong answer, as seen in module 1.

    2. The remaining points

    • Permissions: declare them in cert_lab.permissions.yml; mark restrict access: TRUE when the permission grants admin-equivalent power. Check on the routing, not in the controller.
    • CSRF: any route that changes state over GET (delete, publish via a link) needs _csrf_token: 'TRUE' on the route and the token in the link. Form API forms are protected already.
    • Uploads: validate the extension with file_validate_extensions, store in private:// when the file is sensitive, and never trust the MIME type sent by the client.
    • Secrets: credentials in settings.php or an environment variable, out of Git and out of the exported config.

// settings.php (ignored by Git) or an environment variable

    3. Security that lives in settings.php

    Part of domain 6.0 is not module code: it is environment configuration. Three items show up as scenarios.

    // 1. Trusted host: without this, Drupal accepts any Host header
$settings['trusted_host_patterns'] = [
  '^www\\.example\\.com$',
  '^example\\.com$',
];

    The attack is host header injection: someone sends a request with Host: attacker-site.com, and Drupal, which builds absolute URLs from the received host, writes that domain into the password reset link it emails. The victim clicks and hands over the token. The classic symptom in the question is exactly that: "the links in the recovery email point to another domain".

    // 2. Secrets out of the repository

// 3. Private files outside the docroot
$settings['file_private_path'] = '/var/www/private';

    Working with the community

    The easiest domain to get right: the answer is almost always the one that gives work back to the community.

    Environments, dependencies and incidents

    Covers questions 2, 5, 9, 11 and 15.

    1. A dependency that exists only in dev

    Debug modules (Devel, Webprofiler) must not reach production, but they still need to be versioned so the whole team installs the same thing. Composer splits that into two lists, and the flag decides which one the package lands in.

    composer require --dev drupal/devel        # goes into require-dev
composer require drupal/pathauto           # goes into require

# on the production deploy
composer install --no-dev                  # skips require-dev entirely
    Written asWhat it does
    composer require --dev drupal/foo✅ writes into require-dev
    composer require-dev drupal/foo❌ no such command
    composer require drupal/foo:1.x-dev❌ that is a development version, and it installs in every environment
    Don't mix them up: --dev is about where the package gets installed. x-dev is about which version of the package. The exam puts both in the same question on purpose.

    2. Conflict in composer.lock

    The lock is a generated file: thousands of lines of hashes, written by Composer. Resolving a conflict there line by line produces an invalid lock that installs a combination of packages nobody tested. The two legitimate ways out regenerate the file:

    # way A: restart the branch clean
git rebase --abort
git checkout -b core-update-v2 origin/develop
composer update drupal/core-* --with-all-dependencies

# way B: regenerate the lock mid-rebase
git checkout --ours composer.json
composer update --lock                      # rewrites the lock from the json
git add composer.lock
git rebase --continue

    What is never the answer: putting composer.lock in .gitignore (production loses the guarantee of installing the tested versions) and skipping the conflicting commits (you throw away the very update you were making).

    3. White screen in production

    A WSOD is a fatal PHP error with display switched off. The information already exists, in the log. The expected sequence is to diagnose before acting:

    ActionAssessment
    Read the Apache/PHP error log and watchdog✅ first action, reveals the cause
    Turn display_errors on in production❌ exposes paths and stack traces to any visitor
    Point DNS at stage❌ turns the test environment into accidental production
    Revert the deploy without reading the log⚠️ mitigates, but you redeploy the same bug tomorrow
     
    drush watchdog:show --severity=Error --count=20
tail -n 100 /var/log/apache2/error.log

    4. Vulnerability in a third-party library

    If the maintainer already published the fix, the route is to apply the secure version and deploy. Full stop. A database rollback discards real content, hiding the version number doesn't close the hole, and deferring to the next sprint leaves the site exposed for more weeks.

    5. Getting a patch to RTBC

    RTBC means "reviewed and tested by the community". The mark demands evidence, which is why there are exactly two useful contributions while the patch is failing:

    • Apply the patch, test it and report what happened, with environment and steps. A reproducible report is worth more than a "+1".
    • Debug the failure and post a new patch that fixes the broken tests.

    Marking RTBC with core tests red is a false positive and burns the maintainer's time. Merely following the issue changes nothing about its state.

    PHP, entities and queries

    Covers questions 3, 19 and 20.

    1. Catching more than one kind of exception

    catch chains, from specific to generic. The first matching block wins, so order matters: put Exception first and the blocks below it never run.

    try {
  $response = $this->http->post($url, $payload);
}
catch (RequestException $e) {          // specific first
  $this->logger->warning('API refused: @m', ['@m' => $e->getMessage()]);
}
catch (\Exception $e) {                // generic after
  $this->logger->error('Unexpected failure: @m', ['@m' => $e->getMessage()]);
}
finally {
  // always runs, with or without an exception. Catches NOTHING.
  $this->closeConnection();
}
    Three mistakes the exam builds: handling exceptions inside finally (it doesn't catch, it only executes); nesting catch inside finally (syntax error); and assuming one specific catch covers everything. In PHP 8, fatal errors become \Error, so the widest net is catch (\Throwable $e).

    2. The two live ways to query entities

    // ✅ 1: through the storage
$ids = \Drupal::entityTypeManager()->getStorage('node')->getQuery()
  ->accessCheck(TRUE)->condition('status', 1)->execute();

// ✅ 2: through the static shortcut
$ids = \Drupal::entityQuery('node')
  ->accessCheck(TRUE)->condition('status', 1)->execute();

// ❌ entity.manager: deprecated in D8.7, removed in D9
$ids = \Drupal::service('entity.manager')->getStorage('node')->getQuery();

// ❌ EntityFieldQuery with entityCondition/fieldCondition: Drupal 7
$ids = \Drupal::entityFieldQuery()->get('node')->fieldCondition('field_x', 'value', 1);

    Inside a class, both become an injection of entity_type.manager. The static call is only justified in a procedural file. And accessCheck() stays mandatory on both routes.

    3. Changing and persisting an entity

    To change a field value on a loaded entity, the method is set() (or the specific setter, where one exists). To persist, save().

    $node = Node::load(1);

$node->set('title', 'New title');     // ✅ changes the value on the object
$node->setTitle('New title');         // ✅ equivalent, specific setter

$node->save();                        // writes to the database

// ❌ neither exists
entity_update($node);
$node->setTitle('x')->update();
    Written asAssessment
    $entity->set("title", "New title");✅ correct way to change it
    $entity->title->value = "..."; entity_update($entity);❌ entity_update() does not exist
    $entity->setTitle("...")->update();❌ update() is not an entity method
    $entity->title = "..."; $entity->save()❌ direct assignment is not the canonical form
    In practice: set() alone only touches memory. Real code always ends in $entity->save(). The question isolates the changing step, but in your module the two lines travel together.

    Module life cycle: config, entities and services

    Covers questions 4, 14 and 16.

    1. Config that must disappear on uninstall

    YAML in config/install/ is created when the module is installed. On uninstall, Drupal calculates each config entity's dependencies and removes on its own everything that depends on the departing module. You don't have to write anything for that to happen.

    # config/install/field.storage.node.field_heart_rate.yml
langcode: en
status: true
dependencies:
  module:
    - node
id: node.field_heart_rate
field_name: field_heart_rate
entity_type: node
type: integer
    OptionAssessment
    Drupal deletes them by default on uninstall✅ that is what the config dependency manager does
    hook_schema in .install❌ defines database tables, not config entities
    hook_uninstall deleting via config.factory❌ redoes by hand what core already does, and the list goes stale
    enforced dependency in the YAML⚠️ a real mechanism, but for a different case

    So when does enforced come in? When the config would not naturally depend on your module and you want to tie it anyway:

    dependencies:
  enforced:
    module:
      - health_tracker      # explicitly ties it to the module
    Read the stem: the question asks what ensures removal of config the module itself created. The answer is that Drupal already does it. enforced reinforces the edge case, it isn't the requirement.

    2. A revisionable custom entity

    Declaring the revision keys prepares the schema. Two pieces are missing, and the question tests both.

    Piece 1: the base class. The revision_created, revision_user and revision_log_message fields are declared in baseFieldDefinitions() on RevisionableContentEntityBase. If your class doesn't extend that base, the fields don't exist.

    use Drupal\Core\Entity\RevisionableContentEntityBase;

#[ContentEntityType(
  id: 'eco_track',
  revision_table: 'eco_track_revision',
  entity_keys: ['id' => 'id', 'revision' => 'vid'],
  revision_metadata_keys: [
    'revision_user' => 'revision_uid',
    'revision_created' => 'revision_timestamp',
    'revision_log_message' => 'revision_log',
  ],
)]
class EcoTrack extends RevisionableContentEntityBase {   // ← piece 1

    Piece 2: populating them as the revision is created. hook_entity_revision_create() runs while the new revision is assembled, and that is where the values go in.

    function eco_track_entity_revision_create(EntityInterface $new, EntityInterface $entity, $keep_untranslatable) {
  if ($new->getEntityTypeId() !== 'eco_track') { return; }

  $new->setRevisionCreationTime(\Drupal::time()->getRequestTime());
  $new->setRevisionUserId(\Drupal::currentUser()->id());
}
    Why the other two don't work: entity types are not registered in services.yml (that is for services), and PHP has no multiple inheritance, so "a plugin extending your class and the base" is not a construct that exists.

    3. A route's _controller

    The canonical form, and the one the exam expects, is class and method separated by double colons:

    # ✅ expected form
_controller: '\Drupal\techgear\Controller\ProductsController::build'

# ⚠️ Drupal also accepts service:method, with a single colon
_controller: 'techgear.products:build'

    In the question, on top of the _controller, the names don't match either: the route calls techgear.products while the YAML registered techgear.products.build. The code is wrong on two counts, and the option marked correct is the one about ::.

    # techgear.services.yml
services:
  techgear.products:              # the ID has to match what the route calls
    class: Drupal\techgear\ProductsController
    arguments: ['@current_user']  # quote the @, or the YAML complains
    When in doubt, use Class::method. It is the form Drupal's documentation uses, it is the one the answer key treats as correct, and it doesn't depend on a service ID staying in sync with the route.

    Performance: caching, widget options and images

    Covers questions 1, 6 and 13.

    1. Cache tag for a block that shows a node

    The question to ask is "what data does this depend on". If the block shows a restaurant, it depends on that node, and the tag comes from the object itself:

    $build = [
  '#markup' => $details,
  '#cache' => [
    'max-age' => 86400,
    'tags' => $restaurant_node->getCacheTags(),   // ['node:42']
  ],
];

    Any save of that node invalidates the entry, including when only the Chef Special changed. The distractors attack from three sides:

    DistractorWhy it fails
    'contexts' => 'node.type'There is no node.type cache context. And a context is "varies by", not "depends on"
    'contexts' => 'node.type:restaurant'Same problem, with invented syntax
    'tags' => 'node.restaurant.field_chef_special'A freely named tag. Nobody invalidates it, so the content is stuck until max-age

    2. A form made slow by its widget options

    Thousands of terms in a hierarchy, with translations, assembled every time the form opens. The data is expensive to build and practically immutable: that is the definition of something to cache. Since term labels vary by language, the key includes the language.

    $langcode = $this->languageManager->getCurrentLanguage()->getId();
$cid = 'techgear:organization_options:' . $langcode;

if ($cache = $this->cache->get($cid)) {
  $options = $cache->data;                   // hit: doesn't build the tree at all
}
else {
  $options = $this->buildTermTree($langcode);
  $this->cache->set($cid, $options, Cache::PERMANENT, ['taxonomy_term_list']);
}

    Why the others don't solve it:

    • Hard-coded list in the plugin — breaks the first time a term is edited, and mixes content into code.
    • Views entity reference — swaps where the options come from, but the heavy query still runs on every request.
    • #lazy_builder — defers rendering a fragment. A select element needs its options while the form is being built, so there is nothing to defer.

    3. Twelve images of several megabytes

    The bottleneck is bytes on the wire, and caching doesn't reduce bytes: it reduces processing. Drupal's tool for this is an image style, which generates the derivative at the right size, once, and applies to everything editors upload later.

    Structure → Image styles → add style
  effect: Scale → width 800px

Structure → Content types → Article → Manage display
  image field → format: Image → style: the one you created
    Chain of reasoning: a heavy image is a served file size problem. Caching, BigPipe and aggregation attack processing time and request count, not image weight. A separate thumbnail field and manual reprocessing push recurring work onto people.

    Access, private files and redirects

    Covers questions 8, 10 and 12.

    1. A confidential file

    The decision is in the storage scheme, before any code. A file in public:// sits inside the docroot and is delivered by the web server without going through Drupal: no hook ever runs.

    SchemeWho delivers itCan access be controlled?
    public://Apache/Nginx, straight from diskNo
    private://Drupal, through a routeYes, via hook_file_download()
     
    // settings.php
$settings['file_private_path'] = '/var/www/private';   // outside the docroot

    // cert_lab.module
function cert_lab_file_download($uri) {
  if (strpos($uri, 'private://confidential/') !== 0) {
    return NULL;                     // not mine, another module decides
  }
  if (!\Drupal::currentUser()->hasPermission('download confidential files')) {
    return -1;                       // -1 denies the download
  }
  return ['Content-Type' => 'application/pdf'];   // headers = allowed
}

    A token in the query string is security by obscurity: the link leaks into server logs, browser history and the Referer header. And hook_file_access() is not the hook for private file downloads.

    2. Restricting a View to a role

    Views already has access control on the display itself, and that is what becomes the requirement on the generated route:

    Edit the view → Page settings section → Access
  Permission: pick a named permission          ← preferable
  Role: tick "store administrator"             ← accepted, and it is the answer to the question

    Touching the generated route from outside duplicates the rule and gets lost the next time the view is saved. hook_preprocess_view() runs after the query, once the sensitive data has already been read. And writing a module to define role and permission reimplements what the UI already gives you.

    By permission or by role? In real life, prefer permission: roles change over time and permission is what code should check. On the exam, when the stem literally says "restricted to role X", the option that configures Access on the view is the right one.

    3. Redirecting by query string

    It has to happen early, before rendering, and it depends on something that only exists at runtime: the request parameters. That is KernelEvents::REQUEST.

    class RedirectSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    return [KernelEvents::REQUEST => ['onRequest', 30]];
  }

  public function onRequest(RequestEvent $event): void {
    if (!$event->isMainRequest()) { return; }

    $campaign = $event->getRequest()->query->get('campaign');
    if ($campaign === 'promo' && $this->currentUser->isAnonymous()) {
      $event->setResponse(new RedirectResponse('/promotion'));   // cuts the cycle
    }
  }
}
    OptionWhy not
    Route subscriber with alterRoutes()Runs while the route collection is built, not per request. Never sees the query string
    JS through hook_page_attachmentsThe whole page loads before the redirect. Bad for performance and for SEO
    hook_init()Has not existed since Drupal 8

    Presentation layer: templates, media and widgets

    Covers questions 7, 17 and 18.

    1. Extending a module's template

    Drupal registers a Twig namespace for every installed module and theme. That is why the physical path never appears in a template.

    {# bar/templates/foo-element.html.twig #}
{% extends "@foo/foo_element.html.twig" %}

{% block content %}
  <div class="bar-wrapper">{{ parent() }}</div>

    modules/contrib/foo/templates/...❌ physical path, breaks if the module moves
    foo_element.html.twig❌ resolves to the theme's own template: recursion
    Building the path in preprocess❌ reinvents in code what the namespace already does

    2. Alt text fallback on Media images

    Missing alt is a display problem, about data living on the Media entity. Media preprocess is the layer that runs for every rendering, of old content and new:

    return;
  }

  $item = $media->get('field_media_image')->first();
  if (empty(trim($item->alt))) {
    $item->alt = $media->label();      // media title as the fallback
  }
