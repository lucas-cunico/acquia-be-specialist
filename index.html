    PHP orientado a objetos que o Drupal 11 assume

    Por que quase todo código de módulo virou classe, e o que o Drupal espera dessas classes.

    No Drupal 7, um módulo era um monte de funções soltas dentro de um arquivo .module. Do Drupal 8 em diante isso mudou: a maior parte do código virou classe, e o Drupal deixou de chamar suas funções para instanciar suas classes. Entender essa inversão é o que torna o resto do curso natural.

    1. Onde o arquivo mora define o namespace

    O Drupal usa autoload PSR-4: ele descobre o arquivo de uma classe a partir do nome dela, sem você declarar nada. A regra é fixa — o diretório src/ do seu módulo corresponde ao namespace Drupal\nome_do_modulo, e cada subpasta vira mais um nível.

    ArquivoNamespace + classe
    cert_lab/src/CertLabHelper.phpDrupal\cert_lab\CertLabHelper
    cert_lab/src/Controller/PaginaController.phpDrupal\cert_lab\Controller\PaginaController
    cert_lab/src/Plugin/Block/MeuBlock.phpDrupal\cert_lab\Plugin\Block\MeuBlock

    Se o namespace não bate com o caminho, a classe simplesmente "não existe" para o Drupal — erro de class not found sem nenhuma pista melhor. É a causa nº 1 de módulo que não instala.

    2. Interface é contrato, classe é implementação

    Uma interface lista os métodos que alguém promete ter, sem dizer como. Isso importa no Drupal porque o framework quase nunca quer saber qual classe você usou — quer saber se ela cumpre o contrato.

    // src/CertLabHelperInterface.php — o contrato
<?php
namespace Drupal\cert_lab;

interface CertLabHelperInterface {
  // só a assinatura. Sem corpo.
  public function ultimosArtigos(int $limite): array;
}

    // src/CertLabHelper.php — a implementação
<?php
namespace Drupal\cert_lab;

use Drupal\Core\Session\AccountInterface;

class CertLabHelper implements CertLabHelperInterface {

  // Promoção de propriedade (PHP 8): declara e atribui de uma vez.
  // Equivale a criar $this->currentUser e fazer a atribuição no corpo.
  public function __construct(
    protected readonly AccountInterface $currentUser,
  ) {}

  public function ultimosArtigos(int $limite): array {
    // ...
    return [];
  }
}

    3. A regra de ouro: type hint contra interface

    Repare que o construtor pede AccountInterface, não User. Essa escolha aparece em várias questões da prova, então vale entender o motivo em vez de decorar.

    • Substituível: o Drupal pode entregar o usuário logado, um usuário anônimo ou um objeto proxy. Todos cumprem AccountInterface. Se você exigisse User, quebraria com os outros dois.
    • Testável: em um teste você passa um mock que implementa a interface — não precisa de banco de dados nem de um usuário real.
    • É o padrão do core: quase todo service do Drupal tem sua interface (EntityTypeManagerInterface, ConfigFactoryInterface, MessengerInterface). O PHPCS com DrupalPractice reclama quando você foge disso.

    Como isso aparece na prova: quatro assinaturas de construtor, e a correta é a que recebe a interface.

    // ✅ recebe a interface
public function __construct(AccountInterface $currentUser) {}

// ❌ classe concreta: quebra com usuário anônimo e com o objeto proxy
public function __construct(User $currentUser) {}

// ❌ não recebe nada e vai buscar: dependência escondida, teste impossível
public function __construct() {}
public function algo() { $u = \Drupal::currentUser(); }

// ❌ recebe um array genérico: perde o type hint e o autocomplete
public function __construct(array $config) {}

namespace Drupal\cert_lab;

use Drupal\Core\StringTranslation\StringTranslationTrait;

class CertLabHelper {
  use StringTranslationTrait;      // trait: "cola" métodos na classe

  public function rotulo(string $nome): string {
    // ✅ o trait deu o método t() a esta classe
    return $this->t('Olá, @nome', ['@nome' => $nome]);

    // ❌ concatenação: o tradutor recebe a string quebrada
    // return $this->t('Olá, ' . $nome);
  }
}
    Sobre $this->t(): quando sua classe estende uma base do Drupal ou usa StringTranslationTrait, você chama $this->t('texto') em vez da função global t(). Em arquivos procedurais, t() continua válido. Os dois nunca recebem variável concatenada — sempre placeholder.

    Services e dependency injection

    O conceito mais transversal do Drupal moderno. Ele reaparece em plugin, form, controller e teste.

    1. O problema que a injeção resolve

    Imagine uma classe que precisa saber quem é o usuário logado. A tentação é buscar essa informação lá dentro:

    // ❌ a classe vai buscar o que precisa
class Relatorio {
  public function gerar() {
    $user = \Drupal::currentUser();   // dependência escondida
  }
}

    Funciona — e é errado por três motivos concretos, não por purismo:

    • A dependência fica invisível. Olhando a assinatura da classe, ninguém sabe que ela precisa do usuário atual. Só descobre lendo o corpo de todos os métodos.
    • O teste fica impossível de isolar. \Drupal::currentUser() exige um container inicializado. Você não consegue mais escrever um Unit test.
    • Não dá para trocar a implementação. Um módulo que quisesse decorar esse service não tem por onde entrar.

    A alternativa é inverter: a classe declara o que precisa e alguém entrega. Isso é dependency injection.

    // ✅ a classe recebe o que precisa
class Relatorio {
  public function __construct(
    protected AccountInterface $currentUser,
  ) {}
}

    2. Quem entrega: o service container

    O container é um catálogo de objetos reutilizáveis do site. Cada entrada tem um nome (o service ID), uma classe, e a lista de outros services que ela precisa receber. O container monta o grafo inteiro sozinho e só instancia o que for realmente usado no request.

    # cert_lab.services.yml — na raiz do módulo
services:
  cert_lab.helper:                              # service ID: use o prefixo do módulo
    class: Drupal\cert_lab\CertLabHelper
    arguments:
      - '@current_user'                         # @ = outro service
      - '@entity_type.manager'

    A ordem dos arguments tem que bater exatamente com a ordem dos parâmetros do construtor. Discrepância aí gera um TypeError na hora em que o service é instanciado — não na hora do cache rebuild.

    Services que você vai reencontrar o curso inteiro:

    Service IDPara que serve
    entity_type.managerObter storage e handlers de qualquer entidade
    current_userUsuário da sessão e suas permissões
    config.factoryLer e gravar configuração
    logger.factoryEscrever no log do site
    messengerMensagens de status na tela
    databaseConexão para queries que não são de entidade
    rendererTransformar render array em HTML
    cache.defaultBin de cache para dados próprios

    3. Como uma classe do Drupal recebe a injeção

    Um service comum recebe tudo pelo construtor, e pronto. Mas controllers, forms e plugins não são instanciados por você — o Drupal os cria. Para esses, existe um método estático de fábrica: create().

    <?php
namespace Drupal\cert_lab\Controller;

use Drupal\Core\Controller\ControllerBase;
use Drupal\Core\Entity\EntityTypeManagerInterface;
use Symfony\Component\DependencyInjection\ContainerInterface;

class CertLabController extends ControllerBase {

  // 2º: o construtor apenas recebe e guarda
  public function __construct(
    protected EntityTypeManagerInterface $entityTypeManager,
  ) {}

  // 1º: o Drupal chama este método, que puxa do container
  //     e devolve a instância já montada
  public static function create(ContainerInterface $container) {
    return new static(
      $container->get('entity_type.manager'),
    );
  }

  // 3º: os métodos usam a propriedade, nunca \Drupal::
  public function pagina() {
    $nodes = $this->entityTypeManager->getStorage('node')->loadMultiple();
    return ['#markup' => count($nodes)];
  }
}

    new static() em vez de new self() é proposital: garante que, se alguém estender sua classe, a subclasse é que será instanciada.

    O nome do método de fábrica muda um pouco conforme o tipo de classe, mas o padrão é sempre o mesmo:

    Tipo de classeInterface a implementarAssinatura
    Controller, FormContainerInjectionInterfacecreate($container)
    Plugin (block, formatter…)ContainerFactoryPluginInterfacecreate($container, $configuration, $plugin_id, $plugin_definition)
    Service comumnenhumasó o construtor; o YAML resolve
    Cai muito: o \Drupal:: estático só é aceitável em arquivos procedurais — .module, .install, .theme — onde não existe container disponível para injetar. Em qualquer classe, é injeção. Se uma alternativa usa \Drupal:: dentro de uma classe, ela quase sempre é a errada.

    4. Estender o comportamento de um service existente

    Cenário recorrente: "como alterar o comportamento de um service do core sem hackear o core". Três mecanismos, do menos ao mais invasivo.

    Decorator — seu service embrulha o original. Você intercepta os métodos que quiser e delega o resto. É o caminho preferido, porque o original continua intacto e outro módulo pode decorar por cima do seu.

    # cert_lab.services.yml
services:
  cert_lab.mail_decorator:
    class: Drupal\cert_lab\Mail\MailDecorator
    decorates: plugin.manager.mail          # qual service embrulhar
    arguments: ['@cert_lab.mail_decorator.inner']   # .inner = o original

    <?php
namespace Drupal\cert_lab\Mail;

use Drupal\Core\Mail\MailManagerInterface;

class MailDecorator implements MailManagerInterface {

  public function __construct(
    protected MailManagerInterface $inner,   // o service original
  ) {}

  // o método que você quer mudar
  public function mail($module, $key, $to, $langcode, $params = [], $reply = NULL, $send = TRUE) {
    if ($this->ambienteDeTeste()) {
      $to = 'qa@empresa.com';               // intercepta
    }
    return $this->inner->mail($module, $key, $to, $langcode, $params, $reply, $send);
  }

  // todo o resto simplesmente delega
  public function getInstance(array $options) {
    return $this->inner->getInstance($options);
  }
}

    Repare no nome @cert_lab.mail_decorator.inner: ao compilar o container, o Drupal renomeia o service original com o sufixo .inner e entrega no seu construtor. Você delega para ele em tudo que não quer mudar.

    ServiceProvider — altera a definição de um service no container. Use quando o decorator não resolve, por exemplo para trocar a classe de um service que não tem interface adequada. O arquivo tem nome e lugar fixos: src/CertLabServiceProvider.php, com a classe nomeada a partir do módulo em CamelCase.

    <?php
namespace Drupal\cert_lab;

use Drupal\Core\DependencyInjection\ContainerBuilder;
use Drupal\Core\DependencyInjection\ServiceProviderBase;
use Symfony\Component\DependencyInjection\Reference;

class CertLabServiceProvider extends ServiceProviderBase {

  public function alter(ContainerBuilder $container) {
    if ($definicao = $container->getDefinition('breadcrumb')) {
      // troca a classe que implementa o service
      $definicao->setClass('Drupal\cert_lab\CertLabBreadcrumbBuilder');
      $definicao->addArgument(new Reference('entity_type.manager'));
    }
  }
}

    Tags — não substituem nada. Registram seu service em uma coleção que o Drupal já consome, e o core chama todos os inscritos. É assim que event subscribers, breadcrumb builders e param converters se anunciam.

    services:
  cert_lab.subscriber:
    class: Drupal\cert_lab\EventSubscriber\CertLabSubscriber
    tags:
      - { name: event_subscriber }

  cert_lab.breadcrumb:
    class: Drupal\cert_lab\CertLabBreadcrumbBuilder
    tags:
      # priority maior é consultado primeiro
      - { name: breadcrumb_builder, priority: 100 }
    Como escolher: quer mudar o comportamento de um service? Decorator. Quer somar uma implementação a uma coleção que o core já percorre? Tag. Só quando nenhum dos dois serve, ServiceProvider.

    Routing: da URL ao controller

    O caminho que um request percorre até virar HTML — e os pontos onde você entra nesse caminho.

    1. O ciclo de request, em sete passos

    Saber esta sequência responde sozinha várias questões de troubleshooting e de performance, porque quase toda pergunta do tipo "por que isso não acontece" é uma pergunta sobre em que passo você tentou intervir.

    #PassoOnde você pode entrar
    1index.php monta o kernel e o container—
    2Page cache responde direto, se for anônimo e houver hitMetadados de cache (módulo 5)
    3Evento kernel.requestEvent subscriber
    4Router casa o path com uma rota; parâmetros viram objetos*.routing.yml, param converter
    5Checagem de acesso da rota_permission, _custom_access
    6Controller roda e devolve um render arraySeu controller
    7Renderer transforma em HTML; evento kernel.responsePreprocess, Twig, event subscriber

    Repare no passo 5: o acesso é decidido antes do controller. É por isso que checar permissão dentro do controller é considerado errado — você está intervindo tarde demais.

    2. Anatomia de uma rota

    Uma rota liga um caminho a um callable e a uma regra de acesso. Tudo em cert_lab.routing.yml.

    cert_lab.report:
  path: '/cert-lab/report/{node}'
  defaults:
    _controller: '\Drupal\cert_lab\Controller\CertLabController::report'
    _title: 'Relatório'
  requirements:
    _permission: 'access content'
  options:
    parameters:
      node:
        type: entity:node      # upcasting: {node} chega como objeto Node

    O upcasting de parâmetro é o que transforma o 7 da URL no objeto Node carregado antes do controller rodar. Ele também traz de brinde o 404 automático quando o ID não existe. Sem ele, o método recebe a string crua e você teria de carregar e validar na mão.

    O controller recebe o parâmetro pelo nome, não pela posição:

    public function report(NodeInterface $node) {   // nome bate com {node}
  return ['#markup' => $node->label()];
}

    3. Qual chave de acesso usar

    ChaveQuando
    _permissionAcesso depende só de uma permissão nomeada
    _rolePapel específico. Raro e desencorajado
    _entity_accessnode.view, node.update — delega ao access handler da entidade
    _custom_accessLógica própria. Método retorna AccessResult
    _access: 'TRUE'Público de verdade. Não é lugar de checar acesso depois no controller
     
    requirements:
  _permission: 'access content'                  # uma permissão
  _permission: 'ver relatorio+administer nodes'  # + = OU
  _permission: 'ver relatorio,acessar area'      # , = E

  _entity_access: 'node.update'                  # delega ao handler da entidade
  _custom_access: '\Drupal\cert_lab\Access\RelatorioAccess::check'
  _access: 'TRUE'                                # público
    Por quê importa: checar acesso dentro do controller quebra o sistema. O menu link e o router acham que o usuário pode entrar, o link aparece, e o 403 só surge depois do clique.

    4. Escrevendo um _custom_access

    # na rota
requirements:
  _custom_access: '\Drupal\cert_lab\Access\RelatorioAccess::check'

    public function check(AccountInterface $account, NodeInterface $node) {
  // AccessResult, nunca TRUE/FALSE cru
  return AccessResult::allowedIf($node->getOwnerId() === $account->id())
    ->addCacheableDependency($node)          // a decisão depende do node…
    ->cachePerUser();                        // …e varia por usuário
}

    Três detalhes que a prova cobra: o retorno é um objeto AccessResult (allowed(), forbidden(), neutral()), a decisão carrega seus próprios metadados de cache, e forbidden() é diferente de neutral() — o primeiro veta mesmo que outro módulo permita, o segundo apenas se abstém.

    5. Links e URLs em código

    Nunca escreva a URL como string. Gere a partir do nome da rota, para que ela continue funcionando se o path mudar:

    $url  = Url::fromRoute('cert_lab.report', ['node' => 7]);
$link = Link::createFromRoute($this->t('Ver relatório'), 'cert_lab.report', ['node' => 7]);

// URL vinda do usuário: valide, não confie
$externa = Url::fromUserInput($input);   // rejeita javascript: e afins
    Sintoma comum: rota nova retornando 404. Quase sempre é cache de rota (drush cr) ou indentação errada no YAML. drush route mostra se a rota chegou a ser registrada.

    Composer, patches e atualização de core

    Como o código de terceiros entra no projeto e por que ele nunca é editado à mão.

    1. O projeto inteiro é um pacote

    Drupal moderno é um projeto Composer. O core e todo contrib entram por composer require; vendor/ e web/core nunca são editados à mão nem commitados como fonte de verdade.

    composer require drupal/pathauto:^1.12
composer update drupal/core-* --with-all-dependencies   # atualiza o core

    Dois arquivos governam tudo, e a diferença entre eles cai na prova:

    ArquivoContémQuem edita
    composer.jsonO que você pede: ^1.12, faixas de versãoVocê (ou o comando require)
    composer.lockO que foi resolvido: versão exata de cada pacoteSó o Composer. Mas vai para o Git

    Em produção se roda composer install (respeita o lock, instala o que foi testado), nunca composer update (recalcula versões e pode trazer surpresa).

    2. Patch: correção que ainda não virou release

    Você achou o issue no drupal.org, o patch existe, mas o mantenedor ainda não publicou versão nova. O caminho certo é declarar o patch, com cweagans/composer-patches:

    "extra": {
  "patches": {
    "drupal/pathauto": {
      "#3401234 corrige alias em tradução":
        "https://www.drupal.org/files/issues/2024-01-01/pathauto-3401234-7.patch"
    }
  }
}

    Assim o patch reaplica sozinho em cada composer install e sobrevive ao próximo update. Editar direto o arquivo em contrib perde a correção silenciosamente — e ninguém descobre até o bug voltar em produção.

    3. Atualizar o core com segurança

    Sequência que a prova espera ver:

    composer update drupal/core-* --with-all-dependencies   # 1. baixa o código
drush updatedb                                          # 2. roda hook_update_N pendentes
drush cache:rebuild                                     # 3. reconstrói caches
drush config:export                                     # 4. captura config que o update mudou

    Atualização de patch release (10.3.4 → 10.3.5) é rotina segura: dentro de um minor, o Drupal não introduz quebra de API. Atualização de minor (10.3 → 10.4) pede leitura das release notes. Atualização de major é projeto, com Upgrade Status e correção de código depreciado.

    Git e testes automatizados: o mínimo cobrado

    Dois assuntos leves em peso, mas que rendem questões fáceis de acertar.

    1. Git no fluxo de um projeto Drupal

    Git aparece em cenários de fluxo: feature branch, rebase vs merge, o que entra no repositório. Regra prática do que não se commita: vendor/, web/core, web/modules/contrib, settings.local.php, arquivos de usuário (sites/default/files).

    O que vai para o repositório: seu código custom, o composer.json e o composer.lock, e o diretório de configuração exportada. É essa combinação que torna o site reprodutível — outra pessoa clona, roda composer install e drush cim, e tem o mesmo site.

    2. Os quatro tipos de teste

    Todos rodam por PHPUnit. A diferença é quanto do Drupal cada um liga — e quanto mais liga, mais lento.

    TipoO que sobeUse quando
    UnitTestCaseNada. Só PHPLógica pura, dependências mockadas. Rápido
    KernelTestBaseContainer + bancoService que usa entity storage, config, plugin manager
    BrowserTestBaseSite completo, sem JSFluxo de formulário, permissões, páginas
    WebDriverTestBaseSite + navegador realSó quando precisa de JavaScript/AJAX de verdade
    Padrão da prova: a resposta certa é sempre o teste mais barato que ainda cobre o cenário. Se o cenário menciona entity storage mas não menciona navegador, é Kernel. Se menciona clicar e ver algo aparecer sem recarregar, é WebDriver.

    Onde os arquivos moram: tests/src/Unit/, tests/src/Kernel/, tests/src/Functional/, tests/src/FunctionalJavascript/. A pasta define o namespace e é assim que o runner encontra cada suíte.

    Entity API e Configuration API

    Content entity vs config entity

    A distinção mais cobrada do domínio mais pesado da prova.

    1. O que é uma entidade, afinal

    Entidade é a abstração que o Drupal usa para qualquer "coisa" armazenada: um artigo, um usuário, um termo de taxonomia, uma imagem. Todas expõem a mesma API — load(), save(), delete(), get(), set() — o que permite escrever código que funciona para qualquer tipo.

    Três palavras aparecem o tempo todo e são confundidas:

    • Entity type — a categoria: node, user, media.
    • Bundle — a subdivisão do tipo, com campos próprios: article e page são bundles de node. Nem todo tipo tem bundle (user não tem).
    • Field — o dado em si. Um campo sempre pertence a um bundle e sempre é uma lista de valores, mesmo quando tem um só.
    $node->getEntityTypeId();   // 'node'   → o tipo
$node->bundle();            // 'article'→ o bundle
$node->id();                // 7
$node->label();             // o título

// campo é sempre uma lista: estas três linhas fazem o mesmo
$node->get('field_resumo')->value;
$node->field_resumo->value;
$node->get('field_resumo')->first()->value;

// campo múltiplo
foreach ($node->get('field_tags') as $item) {
  $termo = $item->entity;   // entity reference já carrega o objeto
}

    2. As duas famílias

    São dois sistemas de armazenamento diferentes, com propósitos diferentes.

    Content entityConfig entity
    GuardaConteúdo criado no siteDefinições e estrutura
    Onde viveTabelas próprias no bancoConfig storage, exportável em YAML
    FieldableSimNão
    Revisionável / traduzívelSimNão (config tem override de idioma)
    Exemplosnode, user, taxonomy_term, media, comment, filenode_type, view, image_style, view_mode, field_config, user_role
    Atalho mental: se você espera que aquilo mude entre dev e produção por trabalho editorial, é content. Se você espera que viaje no deploy junto com o código, é config.

    3. O par que confunde: node type e node

    Um content type chamado "Artigo" é uma config entity (node_type): ele define a estrutura, é exportável, e viaja no deploy. Um artigo publicado é uma content entity (node): é conteúdo, fica no banco, e não viaja. A mesma lógica vale para o par vocabulário/termo e para o par view/resultado da view.

    Por isso criar um campo em dev e exportar leva o campo para produção — mas não leva os textos que alguém escreveu nele.

    // config entity: carrega por nome de máquina, e é exportável
$tipo = $this->entityTypeManager->getStorage('node_type')->load('article');
$tipo->label();                       // 'Artigo'

// content entity: carrega por ID numérico, e fica no banco
$node = $this->entityTypeManager->getStorage('node')->load(7);
$node->bundle();                      // 'article' — aponta para o config acima

    Não existe arquivo YAML equivalente para o node 7. Conteúdo não se exporta — se migra.

    Carregar e salvar entidades do jeito certo

    O caminho que passa pelo entity type manager, e por que ele existe.

    1. Storage: a porta de entrada

    Você nunca instancia uma entidade com new nem consulta a tabela dela direto. Tudo passa pelo storage handler daquele tipo, que o entity type manager entrega:

    $storage = $this->entityTypeManager->getStorage('node');

$node  = $storage->load(7);
$nodes = $storage->loadMultiple([7, 8, 9]);        // UMA query
$byVal = $storage->loadByProperties(['type' => 'article']);

    As funções procedurais antigas — node_load(), node_load_multiple(), entity_load() — foram removidas. Se aparecem numa alternativa, é distrator.

    2. Criar, alterar e apagar

    // criar
$node = $storage->create([
  'type'  => 'article',      // o bundle é obrigatório aqui
  'title' => 'Meu artigo',
  'uid'   => 1,
  'field_resumo' => 'texto',
]);
$node->save();                // só agora vai ao banco

// alterar
$node->setTitle('Novo título');
$node->set('field_resumo', 'outro texto');
$node->setPublished();
$node->save();

// nova revisão em vez de sobrescrever
$node->setNewRevision(TRUE);
$node->setRevisionLogMessage('Ajuste de resumo');
$node->setRevisionUserId($uid);
$node->save();

$node->delete();

    create() só monta o objeto em memória; nada é gravado até o save(). É por isso que dá para preencher campos, rodar validação e só então persistir.

    3. O erro de performance que a prova mistura aqui

    // ❌ N+1: uma query por iteração
foreach ($ids as $id) {
  $nodes[] = $storage->load($id);
}

// ✅ uma query para todos
$nodes = $storage->loadMultiple($ids);
    Por que loadMultiple() ganha: uma query em vez de N, e a static cache do storage evita recarregar o que já está em memória naquele request. Em uma tela administrativa com 500 itens, a diferença é de segundos.

    EntityQuery e o accessCheck() obrigatório

    Como consultar entidades sem escrever SQL — e a chamada que virou obrigatória.

    EntityQuery é a forma de perguntar "quais entidades atendem a estas condições". Ela não conhece tabelas: você filtra por campos, e o Drupal traduz para SQL (ou para o que o storage usar).

    $ids = $storage->getQuery()
  ->accessCheck(TRUE)              // obrigatório desde o D10: omitir lança exceção
  ->condition('status', 1)
  ->condition('type', 'article')
  ->sort('created', 'DESC')
  ->range(0, 5)
  ->execute();                     // retorna IDs, não entidades

$nodes = $storage->loadMultiple($ids);

    1. Por que accessCheck() virou obrigatório

    Até o Drupal 9, omitir a chamada significava "sem checagem de acesso" — e sites vazavam conteúdo não publicado sem que ninguém percebesse. A partir do Drupal 10 a decisão passou a ser explícita: sem a chamada, exceção.

    • accessCheck(TRUE) — qualquer listagem que um usuário final vê.
    • accessCheck(FALSE) — apenas quando o bypass é intencional: cron, migração, ou tela administrativa que já é protegida pela própria permissão da rota.
    // ❌ sem a chamada: lança exceção, em vez de devolver resultado sem filtro
$ids = $storage->getQuery()->condition('status', 1)->execute();
// "Entity queries must explicitly set whether the query
//  should be access checked or not."

// ✅ listagem que o usuário vê
$ids = $storage->getQuery()->accessCheck(TRUE)->condition('status', 1)->execute();

// ✅ bypass deliberado, dentro de um cron que precisa ver tudo
$ids = $storage->getQuery()->accessCheck(FALSE)->condition('changed', $ontem, '<')->execute();

    2. Condições que você vai usar

    $q->condition('title', 'Drupal%', 'LIKE');
$q->condition('created', $timestamp, '>=');
$q->condition('field_tags', [3, 7], 'IN');
$q->condition('field_resumo', NULL, 'IS NULL');
$q->condition('field_autor.entity.name', 'Ana');   // atravessa a referência

// OR: um grupo de condições
$grupo = $q->orConditionGroup()
  ->condition('type', 'article')
  ->condition('promote', 1);
$q->condition($grupo);

$total = $q->count()->execute();   // devolve número, não IDs
    Detalhe cobrado: execute() devolve IDs, não entidades. O passo seguinte é sempre loadMultiple(). Quem espera objetos direto do execute() erra a questão.

    3. Quando não é entidade: Database API

    Para tabelas próprias ou consultas que não mapeiam entidades, use o Database API — sempre com placeholders, nunca com concatenação:

    $this->database->select('watchdog', 'w')
  ->fields('w', ['wid', 'message'])
  ->condition('type', $userInput)   // o binding é feito pelo API
  ->execute();

// query com SQL literal: o placeholder :tipo é substituído com segurança
$this->database->query(
  'SELECT wid FROM {watchdog} WHERE type = :tipo', [':tipo' => $userInput]
);

    As chaves em {watchdog} aplicam o prefixo de tabela configurado no site. Concatenar o valor na string é SQL injection — e é o distrator recorrente do domínio de segurança.

    Hooks de CRUD: qual usar

    Onde encaixar código que reage ao ciclo de vida de uma entidade.

    Toda vez que uma entidade é criada, salva ou apagada, o Drupal avisa os módulos por uma sequência de hooks. Escolher o hook certo é escolher o momento certo — e o momento determina se sua alteração persiste ou não.

    Genérico ou específico?

    Cada hook tem duas formas. A genérica roda para toda entidade do site; a específica, só para o tipo indicado no nome:

    function cert_lab_entity_presave(EntityInterface $entity) { }  // todas as entidades
function cert_lab_node_presave(NodeInterface $node) { }        // só nodes
function cert_lab_user_presave(UserInterface $user) { }        // só usuários

    Prefira a específica quando você só se importa com um tipo: menos chamadas por request, e o type hint já vem certo. Use a genérica quando o comportamento vale para tudo (auditoria, por exemplo) — e aí filtre por $entity->getEntityTypeId().

    Detectar se é criação ou edição

    function cert_lab_node_presave(NodeInterface $node) {
  if ($node->isNew()) {
    // primeira gravação
  }
  // valor anterior, disponível só em update
  if (!$node->isNew() && $node->original->label() !== $node->label()) {
    // o título mudou
  }
}

    $entity->original é a versão como estava no banco antes deste save. É a forma padrão de comparar "antes e depois" e aparece em cenários de "só faça X se o campo mudou".

    Hooks em classe, no Drupal 11

    O Drupal 11 introduziu hooks orientados a objeto: em vez de uma função em .module, um método com atributo.

    class CertLabHooks {
  #[Hook('node_presave')]
  public function nodePresave(NodeInterface $node): void { }
}

    A semântica de qual hook usar é idêntica — o que muda é só onde o código mora. As duas formas convivem, e a prova pode mostrar qualquer uma.

    Hook, plugin ou event subscriber?

    Os três mecanismos de extensão do Drupal, e como escolher entre eles sob pressão.

    Cenário recorrente na prova: "qual a forma correta de implementar X". Não é uma pergunta sobre sintaxe — é sobre reconhecer qual dos três mecanismos o Drupal reservou para aquele tipo de problema.

    1. Hook — o ponto de extensão anunciado

    O core executa uma tarefa e, em pontos escolhidos, pergunta aos módulos: "alguém quer opinar?". Cada módulo que implementou aquele hook é chamado, em ordem de peso. É um mecanismo de mão única: você reage ou altera, mas não decide a arquitetura.

    // cert_lab.module — o nome da função É o registro. Não há YAML.
// padrão: nomedomodulo_nomedohook()
function cert_lab_node_presave(NodeInterface $node) {
  // o core chama isto sozinho, toda vez que um node vai ser salvo
}

    2. Plugin — a peça intercambiável

    O Drupal define um contrato ("um bloco sabe se renderizar e se configurar") e permite que qualquer módulo forneça implementações. Depois, alguém escolhe qual usar: o editor escolhe o bloco, o admin escolhe o formatter do campo, a Views escolhe o filtro. Essa escolha é a assinatura do plugin.

    // src/Plugin/Block/MeuBlock.php — a pasta e o atributo fazem o registro
#[Block(id: "cert_lab_meu", admin_label: new TranslatableMarkup("Meu bloco"))]
class MeuBlock extends BlockBase {
  public function build() {
    return ['#markup' => 'olá'];
  }
}
// ninguém chama esta classe. Ela vira uma OPÇÃO na tela de blocos,
// e só roda se um editor escolher colocá-la em uma região.

    3. Event subscriber — a reação a um acontecimento

    Herdado do Symfony. Um objeto despacha um evento e quem se inscreveu é notificado, em ordem de prioridade. Diferente do hook, o subscriber recebe um objeto de evento que ele pode inspecionar, alterar e até usar para interromper a propagação.

    class CertLabSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    return [KernelEvents::REQUEST => ['onRequest', 100]];
  }

  public function onRequest(RequestEvent $event): void {
    // o objeto do evento carrega estado e permite responder
    $event->getRequest()->getPathInfo();
    $event->setResponse(new RedirectResponse('/outro'));
    $event->stopPropagation();     // os de prioridade menor não rodam
  }
}
// + a tag event_subscriber no services.yml, senão nada acontece

    Escrever um plugin: Block

    Um plugin do começo ao fim. O padrão se repete em formatter, widget, condition e migrate.

    1. As três partes de todo sistema de plugin

    • O tipo de plugin — definido pelo core: uma interface, uma classe base e um plugin manager (o service plugin.manager.block).
    • A descoberta — como o manager encontra as implementações. No Drupal 11, por atributo PHP na classe, dentro de src/Plugin/<Tipo>/.
    • A implementação — a sua classe.
    // o manager é um service. Você pode usá-lo diretamente:
$manager = \Drupal::service('plugin.manager.block');   // em classe, injete!

$manager->getDefinitions();              // todos os blocos disponíveis
$plugin = $manager->createInstance('cert_lab_meu', ['limite' => 3]);
$build  = $plugin->build();               // usa o contrato, não a classe

    Repare: quem consome não conhece a sua classe. Conhece o ID e o contrato. É isso que torna o plugin intercambiável.

    Você quase nunca cria um tipo de plugin novo; você fornece implementações para os tipos que já existem. A prova cobra exatamente isso.

    2. A classe completa

    No Drupal 11 a descoberta usa atributos PHP no lugar das anotações em docblock do Drupal 8/9/10.

  ContainerInterface $container,
  array $configuration,
  $plugin_id,

    Event subscribers

    Reagir ao ciclo de request e a eventos despachados por services.

    O padrão vem do Symfony: um objeto despacha um evento, e todos os inscritos são chamados em ordem de prioridade, recebendo o objeto do evento — que eles podem inspecionar e alterar.

    class CertLabSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    // prioridade maior roda antes
    return [KernelEvents::REQUEST => ['onRequest', 100]];
  }

  public function onRequest(RequestEvent $event): void {
    if (!$event->isMainRequest()) { return; }   // ignora sub-requests
    // ...
  }
}

services:

    class: Drupal\cert_lab\EventSubscriber\CertLabSubscriber

      - { name: event_subscriber }   # sem esta tag, nada acontece

    Form API: construir, validar, submeter

    Formulários descritos como array, com validação e submissão em fases separadas.

    1. O ciclo de vida de um formulário

    #FaseO que acontece

    Render arrays em vez de HTML

    A estrutura que atravessa todo o backend do Drupal: descrever a saída, não montá-la.

    1. Por que não devolver HTML direto

    Backend Drupal descreve o que renderizar, não monta string. O render array é um array estruturado que só vira HTML no fim do request. Esse adiamento é o que torna possível:

    • Alterar — outro módulo pode mexer na estrutura antes dela virar HTML.
    • Cachear por pedaço — cada trecho carrega seus próprios metadados de cache.
    • Anexar recursos — CSS e JS sobem junto com o elemento que precisa deles.
    • Escapar corretamente — o renderer sabe o que é texto e o que é markup.
    // ❌ string: nada disso é possível depois
public function pagina() {
  $html = '<ul>';
  foreach ($nodes as $node) {
    $html .= '<li>' . $node->label() . '</li>';   // e sem escape!
  }
  return ['#markup' => $html . '</ul>'];
}

// ✅ estrutura: alterável, cacheável, escapada, com assets
public function pagina() {
  return [
    '#theme' => 'item_list',
    '#items' => array_map(fn($n) => $n->label(), $nodes),
    '#cache' => ['tags' => ['node_list']],
    '#attached' => ['library' => ['cert_lab/lista']],
  ];
}

    Se você concatena HTML no controller, perde os quatro de uma vez. É por isso que a alternativa "monta a string e devolve" está sempre errada.

    2. Anatomia

    Chaves com # são propriedades; chaves sem # são elementos filhos, renderizados em ordem de #weight.

    $build = [
  '#theme' => 'item_list',
  '#items' => $titulos,
  '#title' => $this->t('Artigos'),
  '#attached' => ['library' => ['cert_lab/lista']],
  '#cache' => ['tags' => ['node_list'], 'contexts' => ['user.roles']],
];
    PropriedadeO que faz
    #themeRenderiza por um theme hook e seu template
    #typeElemento de render pré-definido (container, link, table)
    #markupHTML filtrado por Xss::filterAdmin() — só para markup confiável
    #plain_textTexto integralmente escapado — use com input de usuário
    #attachedLibraries, drupalSettings, http headers
    #cacheMetadados de cache: tags, contexts, max-age
    Cai direto: exibir um nome digitado pelo usuário usa #plain_text. #markup ainda deixa passar tags e é vetor de XSS. Não existe #raw.

    3. Elementos filhos e ordenação

    $build = [
  'titulo' => ['#markup' => '<h2>Artigos</h2>', '#weight' => -10],
  'lista'  => ['#theme' => 'item_list', '#items' => $itens, '#weight' => 0],
  'rodape' => ['#markup' => $texto, '#weight' => 10],
];

    Peso menor aparece antes. É assim que módulos inserem conteúdo no meio de uma estrutura montada por outro.

    4. Renderizar na mão (e quando não fazer isso)

    $html = $this->renderer->render($build);

    Chamar o renderer diretamente é raro e perigoso: os metadados de cache do trecho não sobem para a página, e você acaba com conteúdo obsoleto cacheado. O normal é devolver o array e deixar o Drupal renderizar. Se precisar mesmo, existe renderInIsolation() para deixar explícito que o contexto está isolado.

    Theme hooks, preprocess e suggestions

    Da estrutura em PHP até o template Twig — e os pontos onde o tema entra.

    1. O que #theme dispara

    Quando o renderer encontra '#theme' => 'cert_lab_lista', ele procura no theme registry o que fazer: qual template usar e quais funções de preprocess chamar antes. Registrar um theme hook é preencher essa entrada do registry.

    // cert_lab.module — registra um theme hook novo
function cert_lab_theme() {
  return [
    'cert_lab_lista' => [
      'variables' => ['items' => [], 'titulo' => NULL],
      // procura templates/cert-lab-lista.html.twig
    ],
  ];
}

// prepara variáveis para o template
function template_preprocess_cert_lab_lista(&$variables) {
  $variables['total'] = count($variables['items']);
}

    O template correspondente recebe as variáveis já preparadas:

    {# templates/cert-lab-lista.html.twig #}
{# nome do arquivo: theme hook com hífens no lugar de underscores #}
<div class="cert-lab-lista">
  <p>{{ total }} itens</p>
  <ul>
    {% for item in items %}
      <li>{{ item }}</li>
    {% endfor %}
  </ul>
</div>

    2. A cadeia de preprocess

    Várias funções rodam em sequência antes do template, cada uma podendo acrescentar ou ajustar variáveis. A ordem é do mais genérico ao mais específico, e o tema fala por último — por isso o tema sempre pode sobrescrever o módulo:

    template_preprocess_cert_lab_lista()   // 1. o core / quem definiu o hook
cert_lab_preprocess_cert_lab_lista()   // 2. módulos
meu_tema_preprocess_cert_lab_lista()   // 3. o tema ativo — último a falar

    3. Variar um template existente

    Para variar um template que já existe, o mecanismo é theme suggestion, não um theme hook novo:

    function cert_lab_theme_suggestions_node_alter(array &$suggestions, array $variables) {
  $node = $variables['elements']['#node'];
  $suggestions[] = 'node__' . $node->bundle() . '__destaque';
  // habilita node--article--destaque.html.twig
}

    Convenção de nomes: no PHP se usa __ (dois underscores), no arquivo se usa -- (dois hífens). O último item da lista tem a maior prioridade.

    Para descobrir as suggestions disponíveis: ligue o Twig debug em services.yml de dev. O HTML passa a trazer comentários listando os nomes de template candidatos, com o escolhido marcado com x. É a ferramenta padrão para essa tarefa — e mora em dev, nunca em produção.

    Twig: autoescape e o perigo do |raw

    A sintaxe que você precisa reconhecer, e a única regra de segurança que importa aqui.

    1. As três construções

    {{ variavel }}      {# imprime, escapando automaticamente #}
{% if x %}...{% endif %}   {# lógica: if, for, set, block #}
{# comentário, não vai para o HTML #}

    2. Sintaxe do dia a dia

    {{ node.label }}                        {# escapado automaticamente #}
{{ content.field_corpo }}               {# já renderizado e sanitizado pelo text format #}
{{ 'Olá @nome'|t({'@nome': nome}) }}    {# @ escapa, % escapa+enfatiza, : é para URL #}

{% if items %}
  {{ attach_library('cert_lab/lista') }}
  {% for item in items %}
    <li{{ item.attributes }}>{{ item.label }}</li>
  {% endfor %}
{% endif %}

    3. Filtros e testes que caem

    ConstruçãoO que faz
    {{ x|t }}Traduz

    {{ x|length }}, |upper, |trim, |date('d/m/Y') }}Transformações comuns
    {{ x|render }}Força a renderização de um render array
    {{ x|raw }}Desliga o escape. Praticamente nunca

    4. Autoescape: a regra de segurança

    O Twig do Drupal escapa toda saída por padrão. |raw desliga esse escape e é a origem clássica de XSS.

    Se o HTML está "aparecendo como texto" na tela, quase sempre a causa não é falta de |raw — é você estar imprimindo o valor cru do campo em vez do campo renderizado:

    {{ node.body.value }}     {# ❌ o HTML aparece escapado como texto #}
{{ content.body }}        {# ✅ campo renderizado, já sanitizado pelo text format #}

    Essa distinção — node.campo.value é dado cru, content.campo é a saída renderizada — resolve a maior parte dos problemas em que a resposta errada seria |raw.

    Placeholders do t(): @var escapa (padrão), %var escapa e envolve em <em>, :var é só para atributo href. Nunca concatene variável dentro da string traduzível — o texto precisa chegar inteiro ao tradutor.

    Libraries, drupalSettings e behaviors

    Como CSS e JavaScript entram na página, e como o JS do Drupal difere do JS comum.

    1. Library: a unidade de asset

    No Drupal você nunca aponta um arquivo JS solto. Declara uma library — um pacote nomeado com seus CSS, seus JS e suas dependências — e depois anexa a library onde ela for necessária. Assim o Drupal resolve ordem, dependências e agregação sozinho.

    # cert_lab.libraries.yml
lista:
  version: 1.x
  css:
    component:
      css/lista.css: {}
  js:
    js/lista.js: {}
  dependencies:
    - core/drupal
    - core/once
    - core/drupalSettings

    O grupo do CSS (base, layout, component, state, theme) define a ordem de carga e segue o padrão SMACSS adotado pelo Drupal. Componentes ficam em component.

    2. Três formas de anexar

    // PHP: anexa a library e manda dados para o JS
$build['#attached']['library'][] = 'cert_lab/lista';
$build['#attached']['drupalSettings']['certLab']['limite'] = 5;

    {# Twig: quando o template é que sabe que precisa #}
{{ attach_library('cert_lab/lista') }}

    # *.info.yml do tema: carregar em todas as páginas do site
libraries:
  - cert_lab/lista

    Prefira sempre anexar ao elemento que precisa: assim o asset só é baixado nas páginas onde o componente aparece. Carregar tudo global é o erro de performance que a prova associa a este tópico.

    3. O JavaScript do Drupal

    // js/lista.js
(function (Drupal, once, drupalSettings) {
  Drupal.behaviors.certLabLista = {
    attach(context) {
      // roda de novo a cada conteúdo novo vindo por AJAX;
      // once() garante uma única inicialização por elemento
      once('cert-lab-lista', '.cert-lab-lista', context).forEach((el) => {
        el.dataset.limite = drupalSettings.certLab.limite;
      });
    },
  };
})(Drupal, once, drupalSettings);

    Três conceitos, cada um resolvendo um problema específico:

    ConceitoProblema que resolve
    Drupal.behaviorsCódigo precisa rodar também no conteúdo que chega depois, por AJAX
    contextLimita o escopo ao pedaço novo, em vez de varrer a página inteira de novo
    once()Impede inicializar duas vezes o mesmo elemento
    drupalSettingsLeva dados do PHP ao JS com escape correto

    Tags, contexts e max-age

    O assunto mais errado por quem reprova. Vale a pena entender de verdade, não decorar.

    1. O problema do cache, em uma frase

    Guardar o resultado pronto é fácil. Difícil é saber quando jogar fora e quantas versões diferentes guardar. O Drupal responde essas duas perguntas com três metadados, e cada um responde uma pergunta distinta. Confundi-los é o que gera tanto conteúdo obsoleto quanto site lento.

    2. Os três metadados

    MetadadoPergunta que respondeExemplos
    tagsDe quais dados isto depende? Quando eles mudam, invalidenode:7, node_list, config:system.site, user:3
    contextsPor qual dimensão da request isto varia? Guarde uma versão por variaçãouser.roles, user, url.path, url.query_args, languages, theme
    max-agePor quanto tempo continua válido?Cache::PERMANENT, 3600, 0
     
    $build['#cache'] = [
  'tags'     => ['node_list'],       // invalida em qualquer save/delete de node
  'contexts' => ['user.roles'],      // uma variação por conjunto de papéis
  'max-age'  => Cache::PERMANENT,
];
    Armadilha central: 'max-age' => 0 "resolve" qualquer problema de conteúdo desatualizado — e destrói a performance. Quando o cenário diz que uma listagem não atualiza ao publicar conteúdo novo, a resposta certa é a cache tag node_list, não desligar o cache.

    Prefira user.roles a user: variar por usuário cria uma entrada de cache por pessoa; variar por papel cria três ou quatro no site inteiro.

    3. Tags: as que você vai usar

    TagInvalidada quando
    node:7Aquele node específico é salvo ou apagado
    node_listQualquer node é salvo ou apagado
    node_list:articleQualquer node daquele bundle muda
    user:3Aquele usuário é alterado
    config:cert_lab.settingsAquela configuração é salva
    taxonomy_term_listQualquer termo muda

    Você raramente precisa escrever a tag na mão: $node->getCacheTags() devolve ['node:7'], e o padrão para listagens é $storage->getEntityType()->getListCacheTags().

    // invalidar manualmente uma tag própria (raro, mas cai)
Cache::invalidateTags(['cert_lab:relatorio']);

    4. Como decidir, na prova e na vida

    Faça as três perguntas nesta ordem:

    • "De que dados isso depende?" → cada resposta vira uma tag.
    • "Duas pessoas veriam coisas diferentes? Por quê?" → cada "por quê" vira um context.
    • "Isso expira sozinho com o tempo?" → só então max-age. Quase sempre a resposta é não, e fica Cache::PERMANENT.

    Aplicando a um caso concreto — um bloco que lista os 5 artigos mais recentes, com o texto do rodapé vindo das configurações do site, e um aviso extra visível só para editores:

    $build['#cache'] = [
  // P1: depende de quais dados?
  //     → da lista de nodes, e da config do site
  'tags' => ['node_list:article', 'config:system.site'],

  // P2: duas pessoas veriam coisas diferentes? Sim — o editor vê o aviso.
  //     → varia por papel (não por usuário: seriam variações demais)
  'contexts' => ['user.roles'],

  // P3: expira com o tempo? Não. As tags dão conta da invalidação.
  'max-age' => Cache::PERMANENT,
];

    Se em vez disso o bloco mostrasse uma cotação vinda de uma API externa, aí sim entraria 'max-age' => 900: nenhuma tag do Drupal sabe quando a cotação mudou, e o tempo é a única resposta possível.

    Bubbling e dependências de cache

    Por que declarar no componente basta, e como declarar sem esquecer nada.

    Metadados de cache sobem: o que você declara em um pedaço do render array se propaga para o elemento pai e daí para a página. Por isso declarar corretamente no componente basta — você não precisa mexer na página.

    // forma manual
$build['#cache']['tags'] = Cache::mergeTags(
  $build['#cache']['tags'] ?? [], $node->getCacheTags()
);

// forma preferida: a entidade sabe declarar suas próprias dependências
$meta = CacheableMetadata::createFromRenderArray($build);
$meta->addCacheableDependency($node);      // tags + contexts + max-age dela
$meta->addCacheableDependency($config);
$meta->applyTo($build);

    Qualquer objeto que implemente CacheableDependencyInterface — entidades, config, resultados de acesso — pode ser passado a addCacheableDependency(). É a resposta preferida em cenários de "como declarar a dependência corretamente".

    A regra de composição do bubbling é conservadora, e faz sentido: o pai fica com a união das tags e dos contexts dos filhos, e com o menor max-age entre eles. Basta um filho declarar max-age: 0 para a página inteira virar não-cacheável — é assim que um componente mal escrito derruba a performance do site todo.

    Como verificar na prática

    curl -I https://site.test/pagina | grep -i x-drupal-cache

X-Drupal-Cache: HIT              # page cache (anônimo)
X-Drupal-Dynamic-Cache: MISS     # dynamic page cache
X-Drupal-Cache-Tags: node:7 node_list config:system.site
X-Drupal-Cache-Contexts: languages:language_interface theme user.roles

    Se a tag que você espera não está no header, ela não subiu — e a invalidação nunca vai acontecer. É o teste de uma linha para qualquer questão de "por que não atualiza".

    Lazy builders, placeholders e as camadas de cache

    Como isolar o trecho dinâmico para não sacrificar a página inteira.

    Quando um pedaço pequeno e muito dinâmico (o "olá, fulano", o carrinho) obriga a página inteira a variar por usuário, a saída é isolá-lo em um placeholder renderizado à parte.

    $build['saudacao'] = [
  '#lazy_builder' => ['cert_lab.lazy:saudacao', [$uid]],  // só argumentos escalares
  '#create_placeholder' => TRUE,
];

    O service cert_lab.lazy tem um método saudacao($uid) que devolve o render array daquele trecho. Duas exigências que a prova cobra: os argumentos precisam ser escalares (não dá para passar um objeto Node), e o método precisa declarar trustedCallbacks() para o Drupal aceitar chamá-lo.

    Assim o resto da página fica cacheável, e o BigPipe entrega o pedaço dinâmico depois, em streaming.

    Outras alavancas de performance em código

    • Cache próprio para resultados caros: $this->cache->set($cid, $dados, Cache::PERMANENT, $tags) e get() antes de recalcular.
    • Queue API para trabalho pesado: em vez de processar 5.000 itens no request, enfileire e deixe o cron consumir.
    • Batch API quando o usuário precisa ver progresso numa operação longa iniciada na UI.
    • Evitar carregar entidade inteira quando só o ID interessa: getQuery() já devolve IDs.
    // cache próprio para um cálculo caro
$cid = 'cert_lab:relatorio:' . $ano;

if ($item = $this->cache->get($cid)) {
  return $item->data;                       // hit: nem calcula
}

$dados = $this->calcularRelatorioPesado($ano);
$this->cache->set($cid, $dados, Cache::PERMANENT, ['node_list']);
return $dados;

    // trabalho pesado: enfileira em vez de processar no request
$queue = $this->queueFactory->get('cert_lab_reindex');
foreach ($ids as $id) {
  $queue->createItem(['nid' => $id]);      // o cron consome depois
}

    Sanitização: escapar na saída, não na entrada

    O princípio que organiza todo o domínio de segurança do Drupal.

    1. Por que não sanitizar na entrada

    Sanitizar ao gravar parece mais simples, e é errado: você não sabe, na hora de gravar, se aquele dado vai sair em HTML, dentro de um atributo, em um e-mail em texto puro, em JSON ou em um CSV. Cada destino exige um escape diferente. Sanitizar cedo destrói o dado original e ainda protege o destino errado.

    // ❌ escapa na entrada: o dado fica corrompido para sempre
$node->set('field_nome', Html::escape($input));   // grava "Jo&amp;#039;ão"
$node->save();
// o e-mail em texto puro vai mostrar a entidade HTML crua,
// o CSV idem, e um segundo escape na saída duplica tudo

// ✅ grava como veio
$node->set('field_nome', $input);                 // "Jo'ão"
$node->save();

// ...e escapa conforme o destino, na hora de exibir
$build['nome'] = ['#plain_text' => $node->field_nome->value];   // HTML
$assunto = $node->field_nome->value;                            // e-mail: cru

    Princípio do Drupal: guarde o dado como veio, escape no momento de exibir, de acordo com o contexto de saída.

    2. A ferramenta por contexto

    ContextoFerramenta
    Texto em render array'#plain_text'
    Texto em TwigAutoescape (não faça nada)
    String em PHPHtml::escape()
    HTML que precisa manter algumas tagsXss::filter() / Xss::filterAdmin()
    Valor em query SQLPlaceholder do Database API
    URL vinda do usuárioUrl::fromUserInput() — rejeita javascript:
    Distrator clássico: htmlspecialchars() antes de concatenar em SQL. É proteção de saída HTML aplicada na camada errada — não impede SQL injection. Cada camada tem sua ferramenta.

    3. Text formats: quem pode escrever HTML

    No Drupal, a permissão de escrever HTML não é do campo — é do text format. Cada formato tem uma lista de filtros e uma lista de papéis autorizados. Um formato liberado para papel não confiável e com o filtro de XSS desligado é uma porta aberta.

    Três alertas que a prova apresenta como cenário de configuração, não de código:

    • Formato Full HTML disponível para usuários autenticados comuns.
    • Filtro "Limit allowed HTML tags" desativado em um formato de uso público.
    • Permissões como administer filters ou administer users concedidas a papel não administrativo — são equivalentes a acesso total ao site.
    // texto que o usuário escreveu com um text format:
// renderize PELO format, que aplica os filtros configurados
$build['corpo'] = [
  '#type' => 'processed_text',
  '#text' => $node->body->value,
  '#format' => $node->body->format,   // ← o filtro vem daqui
];

// ❌ ignorar o format e jogar no markup: nenhum filtro roda
$build['corpo'] = ['#markup' => $node->body->value];

    Acesso, CSRF, arquivos e atualizações

    O resto do domínio de segurança: o que proteger além da saída de texto.

    1. Declarar e checar permissões

    # cert_lab.permissions.yml
'administer cert lab':
  title: 'Administrar o Cert Lab'
  restrict access: TRUE     # marca a permissão como equivalente a admin

    $account->hasPermission('administer cert lab');   // em código

    A checagem principal, porém, mora na rota — _permission ou _entity_access. Código que checa depois é a resposta errada, como visto no módulo 1.

    2. Os pontos restantes

    • Permissões: declare em cert_lab.permissions.yml; marque restrict access: TRUE quando a permissão dá poder equivalente a admin. Verifique no roteamento, não no controller.
    • CSRF: qualquer rota que altera estado por GET (deletar, publicar por link) precisa de _csrf_token: 'TRUE' na rota e do token no link. Formulários do Form API já vêm protegidos.
    • Uploads: valide extensão com file_validate_extensions, guarde em private:// quando o arquivo é sensível, e nunca confie no MIME enviado pelo cliente.
    • Segredos: credenciais em settings.php ou variável de ambiente, fora do Git e fora da config exportada.
    # rota que altera estado por GET: exige token

    Ferramentas de debug

    O método de diagnóstico que a prova assume: ler o erro antes de mexer no código.

    1. Preparar o ambiente de dev

    Metade dos problemas de "não sei o que está acontecendo" é ambiente que esconde a informação. Um dev bem configurado tem:

    // sites/default/settings.local.php
$config['system.logging']['error_level'] = 'verbose';   // erro completo na tela
$settings['cache']['bins']['render'] = 'cache.backend.null';
$settings['cache']['bins']['page'] = 'cache.backend.null';

    # sites/development.services.yml
parameters:
  twig.config:
    debug: true          # comentários com sugestões de template
    auto_reload: true    # recompila o Twig a cada alteração

    Tudo isso é só dev. Em produção, cada uma dessas linhas é um problema de performance ou de vazamento de informação — e a prova pergunta exatamente isso, como cenário de configuração.

    2. Sintoma → primeiro passo

    SintomaPrimeiro passo

    Escrever um teste

    Como um teste do Drupal se parece, e o que cada base te dá.

    class CertLabHelperTest extends KernelTestBase {

  protected static $modules = ['system', 'node', 'user', 'field', 'cert_lab'];

  protected function setUp(): void {
    parent::setUp();
    $this->installEntitySchema('node');
    $this->installConfig(['cert_lab']);
  }

  public function testListaRespeitaLimite(): void {
    $helper = $this->container->get('cert_lab.helper');
    $this->assertCount(5, $helper->ultimos());
  }
}

    Três detalhes do Kernel test que a prova cobra: $modules lista o que será instalado (e dependências não vêm de graça); installEntitySchema() cria as tabelas da entidade; e $this->container é o container real, então você pega services de verdade.

    Rodar: vendor/bin/phpunit -c web/core modules/custom/cert_lab.

    Como é um Functional test

    class CertLabPaginaTest extends BrowserTestBase {

  protected $defaultTheme = 'stark';
  protected static $modules = ['cert_lab', 'node'];

  public function testAcessoNegadoSemPermissao(): void {
    $this->drupalLogin($this->drupalCreateUser([]));      // usuário sem permissão
    $this->drupalGet('/cert-lab/report/1');
    $this->assertSession()->statusCodeEquals(403);

    $this->drupalLogin($this->drupalCreateUser(['access content']));
    $this->drupalGet('/cert-lab/report/1');
    $this->assertSession()->pageTextContains('Relatório');

}

    drupalGet(), drupalLogin(), submitForm() e assertSession() são o vocabulário básico. Teste de permissão é o exemplo mais citado de algo que só um Functional cobre bem.

    O que a comunidade espera do seu código, e a ferramenta que verifica isso.

    PadrãoVerificaExemplo do que acusa
    DrupalFormatação e documentaçãoIndentação de 2 espaços, docblock em toda função, ordem alfabética dos use, linha em branco no fim do arquivo

    Trabalhar com a comunidade

    O domínio mais fácil de acertar: quase sempre a resposta é a que devolve trabalho à comunidade.

    O caminho canônico quando um módulo contrib tem bug: procurar o issue existente na fila do projeto → se não existir, abrir com passos de reprodução → enviar merge request no GitLab do drupal.org → enquanto não sai release, aplicar por composer-patches.

    Versionamento

    Semantic versioning: 8.x-1.3 (formato legado) ou 2.1.4. Patch corrige, minor adiciona sem quebrar, major pode quebrar API. O core segue um ciclo de minors previsível; cada minor tem janela de suporte definida, e o D11 exige PHP 8.3+.

    "require": {
  "drupal/core-recommended": "^11.1",
  "drupal/pathauto": "^1.12",   // ^ aceita minor e patch: 1.12 → 1.99, nunca 2.0
  "drupal/token": "~1.13",      // ~ aceita só patch: 1.13 → 1.99 do 1.x
  "drupal/metatag": "1.26"      // exato: trava. Evite, impede correção de segurança
}

    # cert_lab.info.yml — declarar compatibilidade do seu módulo
name: Cert Lab
type: module
core_version_requirement: ^10.3 || ^11
dependencies:
  - drupal:node
  - pathauto:pathauto

    Avaliar um módulo contrib antes de adotar

    • Tem release estável compatível com sua versão do core?
    • É coberto pela política de segurança (badge de security advisory coverage)?
    • Fila de issues viva? Último commit recente?
    • Quantos sites usam? Quantos mantenedores?
    • Escrever custom sairia mais barato de manter que adotar e ajudar a manter?
